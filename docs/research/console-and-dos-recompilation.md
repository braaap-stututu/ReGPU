# Recompile the CPU, rebuild the GPU

The short answer: by late 2026, translating the CPU code of any of these sixteen consoles to a modern PC is largely a solved, mechanical problem, and translating the GPU is not. Static recompilers in the N64Recomp mould now ship playable native PC builds for the N64, PS1, Xbox 360, GameCube, Wii, Wii U and Switch. Each one emits literal C, C++ or C# against a register-context struct and links it to a reimplemented OS and graphics runtime ([N64Recomp](https://github.com/N64Recomp/N64Recomp); [XenonRecomp](https://github.com/hedge-dev/XenonRecomp); [RecompOne](https://raw.githubusercontent.com/BlackLabelHQ/RecompOne/HEAD/README.md)). The x86-64 consoles (PS4, PS5, Xbox One) need no CPU recompilation at all, because their code runs natively and the work moves into OS emulation and shader-binary recompilation ([shadPS4](https://github.com/shadps4-emu/shadPS4)). In every generation the hard, unsolved part is the GPU: the PS1's affine rasterizer, the Saturn's forward-mapped quads, the N64's RDP combiner and coverage, the PS2's GS eDRAM, the Xbox 360's eDRAM formats, Flipper's TEV, the PowerVR2's per-pixel translucency sort, and the precompiled AMD and NVIDIA shader binaries of later machines. Three GPU techniques recur across nearly all of them, and each maps directly onto ReGPU-V's Vulkan/D3D12 work. The first is ubershaders combined with persisted or shipped pipeline caches. The second is rasterizer-ordered views or fragment-shader interlock for exact programmable blending. The third is Vulkan compute rasterizers for hardware that has no triangle-GPU equivalent. DOS is the odd case: there is no GPU to translate. The routes are emulation (DOSBox Staging 0.83, DOSBox-X, 86Box), Glide wrappers that put 3dfx titles onto Vulkan or D3D11/12, and, for real high-resolution rendering, source ports or per-game static recompilation. Much 2026 news rests on secondary or self-reported sources. This report flags those claims inline as *(secondary)*, *(unverified)* or *(background, not re-verified in 2026)*.

Read down the "maturity" column and a pattern appears. Platforms whose games call a known, uniform SDK, such as PsyQ on the PS1, libultra on the N64, GX on the GameCube and Wii, and the Xbox 360 kernel, recompile well, because the runtime can replace the SDK instead of emulating registers. Platforms with per-game microcode (PS2 VU, PS3 SPU) or exotic multiprocessor synchronization (Saturn) lag, whatever their age.

## Fifth generation: PS1 recompiles cleanly, Saturn resists everything, N64 set the template

### PS1: integer vertices and ordering tables make it the easiest 3D console to lift

The PS1 is a single-CPU machine. Its **MIPS R3000A-compatible core runs at 33.87 MHz** with exposed load and branch delay slots, a 4 KB I-cache, no data cache, a 1 KB scratchpad and **no FPU**. All 3D maths runs on the fixed-point GTE coprocessor (CP2), which handles matrix-vector multiply-add, perspective transform and Z-averaging for ordering tables ([Copetti, PlayStation Architecture](https://www.copetti.org/writings/consoles/playstation/)). The GPU has 1 MB of VRAM and is effectively a 2D rasterizer. It takes integer screen-space triangles, quads and sprites with **no sub-pixel precision, affine-only texturing, no mipmaps and no Z-buffer**. The CPU sorts primitives into a Z-indexed ordering table of command addresses that is DMA'd to the GPU ([Copetti PS1](https://www.copetti.org/writings/consoles/playstation/)). The famous wobble and texture warping come from the GTE writing integer screen X/Y after an unsigned Newton-Raphson reciprocal divide *(background, not re-verified in 2026)* ([psx-spx GTE](https://problemkaputt.de/psx-spx.htm#geometrytransformationenginegte)).

Games were mostly C built with Sony's GCC-based PsyQ toolchain and linked against libgpu, libgte, libspu and libcd plus a BIOS call table ([Copetti PS1](https://www.copetti.org/writings/consoles/playstation/)). That library uniformity is the platform's great gift to porters, because nearly every game statically links identifiable PsyQ objects that can be found by signature and replaced. Modern homebrew uses PSn00bSDK, whose API deliberately mirrors Sony's ([PSn00bSDK](https://github.com/Lameguy64/PSn00bSDK)).

Emulation is effectively solved. **DuckStation** is the enhanced-play reference. It has D3D11, D3D12, Vulkan, OpenGL and Metal renderers, a CPU recompiler for x86-64, ARMv7, AArch64 and RV64, upscaling, 24-bit colour, texture replacement, and "PGXP for geometry precision, texture correction, and depth buffer emulation" ([DuckStation](https://github.com/stenzek/duckstation)). PGXP is the key GPU-translation idea. It hooks GTE output and CPU loads and stores to carry full-precision float X/Y/Z alongside the 16-bit integers the game writes into GPU commands, so the host renderer gets sub-pixel vertices, perspective-correct texturing via W, and a real depth buffer *(background)* ([libretro Beetle PSX HW docs](https://docs.libretro.com/library/beetle_psx_hw/)). For ReGPU-V, note that DuckStation's licence is now **CC-BY-NC-ND**, which forbids reuse in derived work ([DuckStation](https://github.com/stenzek/duckstation)). Beetle PSX HW and PCSX-Redux are the reusable references.

Decompilation is mature. Its tools are splat, maspsx (which rewrites GCC 2.x output so GNU as reproduces PsyQ objects), decomp.me and objdiff ([maspsx](https://github.com/mkst/maspsx); [sotn-decomp](https://www.github.com/Xeeynamo/sotn-decomp)). **Legend of Mana reports 100% matching for NTSC-U and NTSC-J** ([lom-decomp](https://raw.githubusercontent.com/celophi/lom-decomp/HEAD/README.md)), and Silent Hill is reported at 100% with "no AI-generated code" ([FRVR](https://frvr.com/blog/news/silent-hill-decompilation-with-no-ai-generated-code-has-hit-100-decompilation-reviving-konamis-lost-source-code/)). REDRIVER2 pioneered the API-level porting layer: Psy-X reimplements PsyQ natively and turns a decompiled Driver 2 into a 60 fps Windows/Linux game ([REDRIVER2 wiki](https://github.com/OpenDriver2/REDRIVER2/wiki/Contributing-to-project)). PSY-Z generalizes the idea as a drop-in PSY-Q replacement that "is not an emulator or a static recompiler" ([psyz](https://github.com/Fancy2209/psyz)).

**2026 was the PS1's static-recompilation breakout.** RecompOne statically recompiles MIPS to **C# on .NET 10**. For example, `addiu t0,t0,0x10` becomes `c.T0 = c.T0 + 0x10u;`, and a runtime emulates the BIOS, MMIO, GPU commands and CD-ROM without any Sony files ([RecompOne README](https://raw.githubusercontent.com/BlackLabelHQ/RecompOne/HEAD/README.md); [Time Extension](https://www.timeextension.com/news/2026/07/this-project-is-not-vibe-coded-ps1-recompilation-tool-recompone-goes-live)). Its author describes the central difficulty: PS1 executables mix code and data, so function detection misfires. Without a decomp, porters must locate PsyQ functions and patch them to call the runtime's reimplementations ([readonlymemo interview](https://readonlymemo.com/ps1-recompiled-progress-recompone-pixygarden-interview/)). PSXRecomp was built with Claude Code in under two weeks ([1379.tech writeup](https://hn.jakechampion.name/reader/https://1379.tech/i-built-a-ps1-static-recompiler-with-no-prior-experience-and-claude-code)). It underpins the Spyro "OpenPete" port, which offers 60 fps, true widescreen, no wobble and perspective-correct textures ([Time Extension](https://www.timeextension.com/news/2026/08/ps1-classic-spyro-the-dragon-comes-to-pc-with-the-help-of-ai-assisted-tool-psxrecomp)). A Crash Bandicoot recomp is playable start to finish on Windows and Linux. It also exposes the main limit of widescreen on these titles: geometry that was culled for 4:3 shows up at the screen edges ([Generation Amiga](https://www.generationamiga.com/2026/08/09/crash-bandicoot-ps1-recomp-is-now-fully-playable-on-linux-and-windows/)). None of these projects documents its GPU backend publicly. A Vulkan/D3D12 PS1 layer therefore has to be inferred from emulator design. It needs a 1024×512×16-bit VRAM texture with an upscaled shadow copy and dirty-region tracking for CLUT and framebuffer aliasing, triangle batching with the four semi-transparency modes, PGXP-style or libgte-intercepted precise vertices, and a depth buffer from GTE Z/W.

### Saturn: dual SH-2s and forward-mapped quads defeat triangle GPUs

The Saturn pairs **two Hitachi SH-2s at about 28.63 MHz on one congested 32-bit bus**. Alongside them sit an SCU with a DSP for geometry, a 68EC000 driving the SCSP sound chip, and two video chips ([Copetti, Sega Saturn Architecture](https://www.copetti.org/writings/consoles/sega-saturn/)). VDP1 draws only quadrilaterals by *forward* texture mapping, stamping texels along lines, with no hardware visibility determination. VDP2 has **no framebuffer**: it composites tilemaps and up to two rotation planes on the fly, with VDP1's output as a "sprite" layer ([Copetti Saturn](https://www.copetti.org/writings/consoles/sega-saturn/)). Early documentation was poor, so shipped games mixed C with hand-tuned SH-2 assembly on top of SGL and SBL. Modern homebrew uses Yaul, Jo Engine and the Saturn Ring Library released in April 2025 ([retroreversing](https://www.retroreversing.com/sega-saturn-homebrew-development); [Time Extension](https://www.timeextension.com/news/2025/04/developing-homebrew-games-for-sega-saturn-just-got-a-lot-easier)).

Emulation is still contested. Informal forum consensus treats Mednafen/Beetle Saturn as the accuracy standard but too heavy to upscale ([libretro forum](https://forums.libretro.com/t/ymir-saturn-emulator/49048/54)). **Ymir** (GPL-3) claimed over 90% compatibility in October 2025 and reached v0.3.x in 2026. It needed SH-2 cache emulation and tighter dual-SH-2/SCU synchronization to fix titles such as WipEout ([Time Extension](https://timeextension.com/news/2025/10/new-emulator-ymir-now-boasts-over-90percent-compatibility-with-the-sega-saturns-library); [Ymir releases](https://github.com/StrikerX3/Ymir/releases)). A claim that Ymir v0.4.1 is "best overall" comes from a low-reliability site and is unverified ([tech-insider](https://tech-insider.org/?p=16597)).

The most important 2026 Saturn finding for a GPU project came from Yaba Sanshiro's developer in May 2026, and it is about why the Saturn breaks triangle GPUs. Splitting a VDP1 quad into two triangles distorts the texture along the seam. GPU top-left fill rules also drop the right column and bottom row that VDP1 draws, which leaves one-pixel gaps that become "very visible" at 2× and 4× upscaling. His fix is a **compute-shader rasterizer with one thread per screen pixel** that does VDP1 coverage and texel lookup. It shipped on Android and then Windows, and it reduces but does not eliminate seams in Sega Rally ([SegaSaturnShiro, 15 May 2026](https://www.segasaturnshiro.com/2026/05/15/yaba-sanshiro-rewrites-vdp1-core-to-improve-rendering/); [Windows](https://www.segasaturnshiro.com/2026/05/21/yaba-sanshiro-switches-to-compute-shaders-on-windows/)). Kronos similarly uses compute for VDP2 rotating backgrounds ([libretro Kronos](https://www.libretro.com/index.php/category/kronos/)). Decompilation barely exists. The only notable game effort is Panzer Dragoon Saga: yaz0r's "Azel" (semi-playable, dormant since 2020, now open) and the MIT-licensed "atolm" full decomp ([Time Extension](https://timeextension.com/news/2026/02/a-native-pc-port-of-panzer-dragoon-saga-is-in-early-development); [atolm](https://github.com/blythos/atolm)). **No generic Saturn static recompiler was found.** Master/slave SH-2 handshakes, cache tricks, SCU DSP microcode and uneven SDK use make it the worst recompilation target of its generation.

### N64: the platform that defined modern static recompilation

The N64's Reality Co-Processor splits graphics in two. The **RSP** is a MIPS-derived vector DSP that runs game-supplied microcode for transform, lighting and audio. The **RDP** is a fixed-function rasterizer with 4 KB of TMEM, a programmable colour combiner and blender, 3-bit coverage anti-aliasing, and 1-cycle, 2-cycle, fill and copy modes at 62.5 MHz ([n64brew RDP](https://n64brew.dev/wiki/Reality_Display_Processor); [RDP pipeline](https://n64brew.dev/wiki/Reality_Display_Processor/Pipeline)). Synchronization is the programmer's job, and a wrong render mode can hang the RDP outright ([n64brew RDP](https://n64brew.dev/wiki/Reality_Display_Processor)). The CPU is a VR4300 (MIPS R4300i-derived) with an FPU, plus 4 MB RDRAM expandable to 8 MB *(background, not re-verified)*. Commercial games used libultra with a 32-bit ABI and the IDO or GCC 2.7.2 compilers. Homebrew today uses libdragon (GCC 16, the rdpq RDP library, an RSP mixer) and treats **ares as the only accurate emulator** ([libdragon](https://github.com/DragonMinded/libdragon); [N64Recomp](https://github.com/N64Recomp/N64Recomp)). The libdragon repository appeared archived when captured in November 2026; the reason is unverified.

Emulation is split between accuracy-first LLE and enhancement-friendly HLE. ares and gopher64 (simple64's successor) use no per-game hacks. gopher64 renders through **paraLLEl-RDP**, a Vulkan compute implementation of the RDP that does tile binning on the GPU and specializes a small set of SPIR-V shaders per RDP state with specialization constants ([libretro](https://www.libretro.com/?p=48552); [themaister 2019](https://themaister.net/blog/2019/10/)). Version numbers for gopher64 conflict between secondary sources *(unverified)* ([tech-insider](https://tech-insider.org/gopher64-n64-emulator-setup-2026/)). Even the bit-exact path has blind spots. Paper Mario's pause screen depends on two hardware bugs cancelling out, which paraLLEl-RDP does not reproduce ([SED transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/09/SED1735-N64-Recomp.txt)).

The decompilation scene produced the reference PC-port stack. Majora's Mask reached 100% ([GamesRadar](https://www.gamesradar.com/games/the-legend-of-zelda/after-3-years-these-legend-of-zelda-fans-have-finally-finished-decompiling-the-code-of-majoras-mask-to-help-modders-and-speedrunners-but-theres-still-tons-of-work-to-be-done)). Ports built on **libultraship** include Ship of Harkinian v9.2.3, 2Ship2Harkinian v4.0.2, SpaghettiKart, Starship and Ghostship. libultraship reimplements libultra, externalizes assets to .o2r archives and renders with Fast3D, a display-list interpreter; its README lists OpenGL and Metal backends ([readonlymemo list](https://readonlymemo.com/decompilation-projects-and-n64-recompiled-list/); [libultraship](https://github.com/Kenix3/libultraship)). LLM-assisted matching became normal in 2025–26. Snowboard Kids 2 jumped from about 25% to 58% matched with agents before hitting a "long tail", and later reached 100% ([Chris Lewis](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/); [100%](https://blog.chrislewis.au/snowboard-kids-2-is-100-decompiled/)).

**N64Recomp** is the template every other platform copied. It translates each MIPS instruction to literal C, for example `addiu $r4,$r4,0x20` becomes `ctx->r4 = ADD32(ctx->r4, 0X20);`. Delay slots are duplicated into both paths, `jal` becomes a C call, jump tables become `switch` statements, and `jalr` becomes `LOOKUP_FUNC(ctx->r25)(rdram, ctx)`. Relocatable overlays get `RELOC_HI16/LO16` fixups, and TLB-mapped code is still unsupported ([N64Recomp](https://github.com/N64Recomp/N64Recomp)). The code links against **N64ModernRuntime** (GPL-3), which reimplements libultra threads, message queues, VI, PI DMA and saves rather than recompiling them ([N64ModernRuntime](https://github.com/N64Recomp/N64ModernRuntime)). It also links against **RT64**, an MIT renderer for **D3D12, Vulkan and Metal** ([RT64](https://github.com/rt64/rt64)). Wiseguy describes the goal as behavioural, not binary, equivalence. The runtime must keep exactly one game thread running at a time and reproduce libultra's fixed-capacity, blocking message queues. Clang optimization makes the static output faster than accurate dynarecs ([SED transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/09/SED1735-N64-Recomp.txt)). Audio microcode is recompiled from RSP code using ares' vector reference implementations, while graphics microcode is HLE'd by RT64 ([Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)). As of November 2026 the "AI-free" list counts **about 16 recomp ports**, including Banjo, DK64, Majora's Mask, Star Fox 64 and Mario Kart 64 ([readonlymemo](https://readonlymemo.com/decompilation-projects-and-n64-recompiled-list/)). An aggregator counts 32 playable projects *(secondary)* ([portedgames](https://portedgames.com/recompiled-games/n64/)).

RT64 is the most instructive renderer in this whole report for ReGPU-V. It records the whole frame instead of submitting immediately. It defers memory-reading RDP operations to a full sync so it can detect framebuffer write-backs. It runs RSP vertex transform, lighting and texgen in a compute shader. It uploads TMEM raw and decodes it in compute. It **uses ubershaders to avoid pipeline-compile stutter**. And it runs a dual renderer: one native-resolution pass synced to RAM for readbacks, and one high-resolution replay that can also interpolate to high frame rates by matching draws across frames ([RT64](https://github.com/rt64/rt64)). Widescreen works through an extended GBI, entered via a NOOP command, that lets patched games anchor 2D elements to screen edges ([RT64](https://github.com/rt64/rt64)). Zelda64Recomp's minimum requirements show the API floor this design needs: **D3D12 SM6, Vulkan 1.2 or Metal Argument Buffers Tier 2** ([Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)).

## Sixth generation: the PS2's GS is the hardest GPU, the GameCube the best-ported

### PS2: MIPS is easy; VU microcode and GS eDRAM are not

The PS2 is a DMA-streamed heterogeneous machine. The Emotion Engine's R5900 has 128-bit GPRs with MMI integer SIMD and a **non-IEEE single-precision FPU** that has no NaN or Inf and clamps on overflow. Two VLIW vector units run game-uploaded microcode. VU1 typically transforms geometry and XGKICKs GIF packets to the Graphics Synthesizer. The PS1-class IOP handles I/O and the SPU2 *(background, not re-verified)* ([ps2tek](https://psi-rockin.github.io/ps2tek/)). The GS is where modern GPUs struggle. Its **4 MiB of eDRAM is divided into 8 KiB swizzled pages**. Vertices arrive in window space as 12.4 fixed point. Alpha 0x80 means 1.0, and values up to about 2.0 are legal, which UNORM targets cannot store. Texture LOD comes from log2(Q) rather than derivatives. Games routinely sample the pixels they are rendering to, synchronizing only with an inconsistently used TEXFLUSH, which themaister calls "the root cause of extreme pain" ([themaister, 2024](https://themaister.net/blog/2024/07/)).

Retail games used SCE libraries and hand-written VU microcode. Matching decomps need period compilers such as ee-gcc2.9-991111 or EE GCC 2.95.2, because "modern GCC will NOT byte-match" ([rac1-decomp](https://raw.githubusercontent.com/OpenRAC/rac1-decomp/HEAD/README.md)). Homebrew uses ps2toolchain and ps2sdk ([ps2sdk](https://github.com/ps2dev/ps2sdk)).

**PCSX2 2.8.0 (late August 2026) made D3D12 the default Windows renderer and added Rasterizer Ordered Views support**, along with hardware-mode AA1, a "draw buffering" fix and per-title speedups such as up to 4× in some Gran Turismo 4 scenes. These details come from secondary coverage; the official changelog was not fetched ([gaming-st.com](https://gaming-st.com/news/pcsx2-2-8-direct3d12-release/); [Generation Amiga](https://www.generationamiga.com/2026/08/29/pcsx2-new-update-brings-big-changes-to-the-playstation-2-emulator/); [iXBT](https://ixbt.games/en/news/2026/08/30/431185-pcsx2-280-vysel-emuliaciia-ps2-polucila-bolsoi-apgreid.html)). The hardware renderer's architecture is the standard fixed-function-to-shader recipe *(background, from the PCSX2 source)* ([PCSX2](https://github.com/PCSX2/pcsx2)). GS state is packed into shader-selector bitfields that pick uber-shader permutations. Blends that fixed-function hardware can express go to API blend state, and the rest (Cs−Cd with alpha above 1, colour clipping) fall back to shader blending through framebuffer fetch, render-target copies or barriers, under a user "Blending Accuracy" level. A texture cache resolves the aliasing when a 32-bit render target is read as a 16- or 8-bit texture. Upscaling breaks pixel-exact effects, so PCSX2 exposes per-game half-pixel-offset and sprite-rounding fixes. ROV matters because it gives programmable-blend semantics without per-primitive barriers, which themaister notes "hurt performance badly" on desktop immediate-mode GPUs ([themaister](https://themaister.net/blog/2024/07/)).

The alternative is **paraLLEl-GS**, a Vulkan compute GS rasterizer. It uses a barycentric rasterizer with 32-bit integer edge maths and 8 sub-pixel bits, 32×32 tile binning, and a per-256-byte page tracker of read/write hazards with batched barriers. It serves feedback reads from in-register colour when UVs match pixel positions, which cut Valkyrie Profile 2's barriers from more than 500 to 18. It supports super-sampling with multiple VRAM sample copies ([themaister](https://themaister.net/blog/2024/07/)). Whether any emulator integrated it after mid-2024 is unverified. On Android, ARMSX2 1.0 shipped open source in October 2025 and NetherSX2 remains faster ([Android Authority](https://www.androidauthority.com/armsx2-refresh-ps2-emulator-android-updates-3682200/)).

Native PC builds exist almost only through **OpenGOAL**. It decompiles Naughty Dog's GOAL Lisp output back to source, compiles it with a new x86-64 GOAL compiler, and *rewrites* the VU1/GS renderers as native OpenGL renderers per renderer type instead of emulating them *(mechanism: background)* ([OpenGOAL docs](https://opengoal.dev/docs/developing/decompiling/getting_started)). All three mainline Jak games have been playable natively since 31 March 2026, with Jak 2 and 3 still labelled beta ([Time Extension](https://www.timeextension.com/news/2026/04/all-three-mainline-jak-and-daxter-ps2-games-now-have-native-pc-ports)). Matching decomps for Sly Cooper, Kingdom Hearts, Ratchet & Clank, SSX and others exist, but they sit mostly at low percentages ([sly1](https://raw.githubusercontent.com/TheOnlyZac/sly1/HEAD/README.md)). **PS2Recomp** applies the N64Recomp pattern to the R5900 (`ctx->r4 = ADD32(ctx->r4, 0X20);`). It has an analyzer, an IOP module runner, and a runtime whose README admits "Hardware emulation is partial and many paths are stubbed", with the GS delegated to an external implementation ([PS2Recomp README](https://raw.githubusercontent.com/ran-j/PS2Recomp/main/README.md); [GIGAZINE](https://www.gigazine.net/gsc_news/en/20260130-ps2recomp)). Repeated claims that Sly Cooper is "fully playable" through PS2Recomp come from Mixvale, which could not be fetched, and a skeptical newsletter disputes them, so treat this as **unverified** ([Mixvale](https://www.mixvale.com.br/2026/08/20/open-source-tool-turns-playstation-2-games-into-native-desktop-en/); [Obsolete Sony](https://obsoletesony.substack.com/p/what-is-ps2-recomp)). The structural reason the PS2 lags the N64 is that N64 RSP graphics microcode comes in a few standard families that an HLE renderer can understand, while PS2 VU microcode is per-game. A recompiler must either JIT it at runtime or statically translate each uploaded microprogram, and no documented project translates VU1 into GPU compute.

### Dreamcast: translucency auto-sort becomes order-independent transparency

The Dreamcast pairs a **200 MHz SH-4 with a 4×4 matrix FPU (FTRV)** and store queues with a **PowerVR2 tile-based deferred renderer**. The PowerVR2 takes opaque, punch-through and translucent display lists through a Tile Accelerator and sorts translucent polygons per pixel in hardware *(background, not re-verified)* ([dreamcast.wiki](https://dreamcast.wiki/)). Official development used Sega's Katana SDK with the Hitachi SHC compiler. Homebrew uses KallistiOS ([KallistiOS](https://github.com/KallistiOS/KallistiOS)). Flycast is the active emulator. It emulates per-pixel translucency sorting on OpenGL 4.3+ and Vulkan with per-pixel fragment linked lists, an A-buffer resolved in a sort pass, and falls back to per-triangle sorting on weaker renderers *(background)* ([Flycast](https://github.com/flyinghead/flycast)). For a D3D12 target, ROVs are the natural alternative to linked lists. No Dreamcast port was confirmed to do exact PowerVR2 sorting on D3D12.

The 2026 headline is the **Sonic Adventure decomp: "100% of the game's code builds from source, byte for byte"** for the Japanese v1.007 release (247 binaries, 97.7% C). It runs period SHC 5.0 compilers on Linux through `wibo`, and `make pc` produces a PC build that needs **SDL3 and Vulkan** ([Sonic Adventure README](https://raw.githubusercontent.com/reshaped/sonic-adventure/HEAD/README.md)). SH-4 static recompilation is real but early. dcrecomp converted ChuChu Rocket's 21,624 functions to C. The result boots and renders untextured flat-shaded geometry at about 28 fps, with an interpreted ARM7 sound driver and no textures or input yet. The recompiler had to model FTRV, FLDI0/1 and the banked FP registers explicitly ([chuchu README](https://raw.githubusercontent.com/sp00nznet/chuchu/HEAD/README.md)).

### Original Xbox: x86 that cannot simply run, because the D3D8 runtime is baked in

The Xbox is a 733 MHz Pentium III-class PC with an **NVIDIA NV2A (GeForce 3/4-class)** GPU. Its pixel "shaders" are register-combiner configurations, and it has 64 MB of unified memory. Each game *statically links* the XDK's D3D8-derived libraries, so there is no system D3D DLL to replace *(background, not re-verified)* ([xboxdevwiki](https://xboxdevwiki.net/)). Two emulation philosophies follow. **xemu** (GPL-2.0, QEMU-based, actively developed) is LLE. It emulates the whole machine and translates NV2A vertex programs and combiner state into GLSL or SPIR-V, with Vulkan and OpenGL backends ([xemu](https://github.com/xemu-project/xemu)). **Cxbx-Reloaded** is HLE. It runs the x86 code directly and intercepts signature-matched XDK functions, mapping them to host D3D9 *(background)* ([Cxbx-Reloaded](https://github.com/Cxbx-Reloaded/Cxbx-Reloaded)). Reports of 2026 xemu Vulkan improvements and an SDL3 migration come from an aggregator *(unverified)* ([penguinpulse](https://penguinpulse.pages.dev/news/2026-05-11-xemu-dev-build-updates-vulkan-backend-forces-nvidia-native-p.html)). Microsoft itself now ships original-Xbox games on PC inside an embedded Xbox 360 emulator ("XeFu"), and modders have used those binaries to boot other titles ([PC Gamer](https://pcgamer.com/gaming-industry/game-development/the-new-backward-compatible-xbox-games-on-pc-run-on-an-og-xbox-emulator-inside-an-xbox-360-emulator-and-people-have-already-used-it-to-run-other-xbox-360-games)).

No original-Xbox static recompiler exists, and one would add little: the ISA is already x86, and the hard problems are 32-bit pointer assumptions and NV2A semantics. Native ports come from decompilation. A Halo CE decomp spawned "halo-ce-universal" ports for Linux, Windows and Android (OpenGL 4.5/GLES3, 32-bit x86 on desktop), even though decomp.dev reportedly showed only **7.17% of functions byte-matched**. The ports run non-matching but functional code *(secondary)* ([heldgames Halo CE](https://heldgames.com/guides/halo-ce-native-port-android-handhelds)). A WebAssembly browser port followed in September 2026 ([TechSpot](https://www.techspot.com/news/114042-you-can-now-play-original-halo-browser-128.html)).

### GameCube: a known GX API turned decomps into ports, then recomps

The GameCube's **Gekko (a PPC750 derivative at 486 MHz)** adds paired-singles SIMD, two floats per FPR, with GQR-driven quantized loads. The **Flipper** GPU has a fixed-function transform unit, up to **16 TEV combiner stages** and an embedded framebuffer that games copy to textures or to RAM *(background, not re-verified)* ([YAGCD](https://www.gc-forever.com/yagcd/)). Games call Nintendo's GX library, compiled mostly with Metrowerks CodeWarrior *(background)* ([devkitPro](https://devkitpro.org/)). Some titles go further: the Rogue Squadron games run their own MMU paging, which Dolphin Release 2603 optimized and which the Red Two recomp reimplements ([Dolphin 2603 mirror](https://hn.jakechampion.name/reader/https://dolphin-emu.org/blog/2026/03/12/dolphin-progress-report-release-2603); [heldgames Red Two](https://heldgames.com/guides/rogue-squadron-ii-red-two-recomp)).

**Dolphin is the reference design for turning fixed-function GPU state into shaders.** It generates a specialized shader per unique TEV/XF configuration. The configuration space is too large to precompile, so in 2017 it introduced **ubershaders**: large vertex and pixel shaders that interpret raw GPU state, looping over TEV stages. In "hybrid" mode they draw while specialized shaders compile asynchronously and are swapped in. Explicit pipeline creation in D3D12, Vulkan and Metal helps because it stops drivers deferring compilation to draw time *(older, 2017; page not re-fetched)* ([Dolphin ubershaders](https://dolphin-emu.org/blog/2017/07/30/ubershaders/)). Dolphin's 2026 releases (2603 and 2609) focused on Triforce arcade support, MMU optimizations, Android netplay, and security fixes found through AI-assisted bug hunting ([Notebookcheck](https://www.notebookcheck.net/Dolphin-Emulator-Android-update-adds-cross-platform-netplay-and-improved-rumble-amid-AI-attacks.1407268.0.html)).

The decomp pipeline uses decomp-toolkit (dtk) to split DOL/REL files, objdiff for per-function diffs, and CodeWarrior run through wibo ([decomp-toolkit](https://github.com/encounter/decomp-toolkit); [objdiff](https://github.com/encounter/objdiff)). It produced the year's biggest port. **Twilight Princess reached fully matching in December 2025, and the native "Dusk/Dusklight" port shipped v1.0 around 9 May 2026** for Windows, macOS, Linux, Android and iOS ([Time Extension](https://timeextension.com/news/2026/05/the-legend-of-zelda-twilight-princess-has-unofficially-been-ported-to-the-pc); [GamingOnLinux](https://gamingonlinux.com/2026/05/dusk-is-a-reverse-engineered-reimplementation-of-the-legend-of-zelda-twilight-princess)). Its enabling layer is **Aurora**, an MIT "source-level GameCube and Wii compatibility layer". Aurora reimplements GX on **WebGPU via Chromium's Dawn**, so it targets D3D12, Vulkan and Metal from one backend, and it ships **"transferable" pipeline caches** so release builds avoid first-run stutter. It also covers PAD, DVD (any disc format via `nod`) and CARD ([Aurora](https://github.com/encounter/aurora)). The README does not document how TEV becomes WGSL. The Animal Crossing decomp yielded a PC port in March 2026 that reportedly swaps GX for OpenGL 3.3 and is 32-bit only, a reminder that pointer-size assumptions from 32-bit PPC are the main porting debt ([Notebookcheck](https://www.notebookcheck.net/Animal-Crossing-for-the-Nintendo-GameCube-just-received-an-unofficial-native-PC-release-with-support-for-4K-widescreen.1253295.0.html); [Cozy-Acres](https://github.com/timfox/Cozy-Acres)).

Static recompilation arrived in late 2026. **Red Two (Rogue Squadron II) v1.0 shipped on 18 November 2026** after commits began on 5 November, built by one developer with Claude. It translates PPC ahead of time to C++ with symbol-less function discovery, models VI, DVD and controllers at register level, emulates MusyX audio at command-list level, requires AVX2, and renders through Aurora on D3D12 or Vulkan. The only source is secondary, and its author did not run the builds ([heldgames Red Two](https://heldgames.com/guides/rogue-squadron-ii-red-two-recomp)). The same source lists Luigi's Mansion Recompiled (>v1.1) and Skies of Arcadia Legends (beta). No primary source explains how any of these recompilers handles paired-single quantization or FPSCR rounding exactness.

## Seventh generation: SPUs and eDRAM are the walls, Xbox 360 recomp is real

### Wii: Dolphin's GameCube work carries over, plus the first Wii recomp

The Wii is a faster GameCube. It has a 729 MHz Broadway CPU and a 243 MHz Hollywood GPU with the same TEV/EFB model, 24 MB 1T-SRAM plus 64 MB GDDR3, and a Starlet ARM core running IOS for I/O and security *(background, not re-verified)* ([WiiBrew](https://wiibrew.org/wiki/Hardware)). One GX reimplementation therefore covers both consoles, and Dolphin and Aurora both do exactly that. Wii decomps (Skyward Sword, Mario Kart Wii, Super Mario Galaxy, Brawl) use the same dtk toolchain *(background; progress not verified)* ([zeldaret](https://github.com/zeldaret)). **Mario Kart Wiicompiled**, announced 15 July 2026 and at v0.2.32 by 14 September, bills itself as the first static recompilation of a Wii game: "No emulator in the loop, no interpreter, no JIT". It runs on Windows, Linux x64/ARM64 and Apple Silicon, needs the PAL disc, and states that it was built with AI tools ([Tom's Hardware](https://www.tomshardware.com/video-games/retro-gaming/mario-kart-wii-recompiled-for-pc-using-ai-with-4k-potential-and-uncapped-frame-rates-first-static-recompilation-of-a-wii-game-supports-over-200-tracks-thanks-to-retro-rewind-compatibility)). Its GX backend and paired-singles handling are unpublished. General toolkits (DolRecomp, NWiiRecomp, the Rust-emitting gcrecomp) exist, but their authors warn they are not drop-in ([GBAtemp](https://gbatemp.net/posts/10875886/); [gcrecomp](https://lib.rs/crates/gcrecomp-cli)).

### PS3: the Cell's SPUs make both emulation and recompilation hard

The Cell combines one dual-issue in-order PowerPC PPE with VMX and **six game-usable SPEs**. Each SPE is a 128-register SIMD core with a **256 KB software-managed local store** that reaches main memory only through MFC DMA of up to 16 KB per transfer, and has no branch prediction ([Wikipedia: Cell](https://en.wikipedia.org/wiki/Cell_(processor))). The RSX is a G70-derived NVIDIA GPU with split vertex and pixel pipelines and 256 MB of GDDR3 *(background, not re-verified)*. Games drove it through libgcm command buffers and scheduled SPU work through the SPURS job runtime. Homebrew uses PSL1GHT ([PSL1GHT](https://github.com/ps3dev/PSL1GHT)).

**RPCS3 reported about 80% of tracked titles "Playable" on 21 October 2026**, up from 70% in January ([GamingOnLinux](https://www.gamingonlinux.com/2026/07/playstation-3-emulator-rpcs3-gets-75-percent-of-all-games-playable-on-pc/); [Wikipedia: RPCS3](https://en.wikipedia.org/wiki/RPCS3)). One outlet claims every title now at least reaches in-game *(secondary)* ([Overclock3D](https://overclock3d.net/?p=315095)). RPCS3 recompiles SPU code to x86 through LLVM and ASMJIT, and SPU emulation is its largest CPU bottleneck. In April 2026 a "Cell breakthrough" added codegen for newly recognized SPU patterns, worth 5–7% average FPS across all CPUs ([Tom's Hardware](https://www.tomshardware.com/video-games/playstation/rpcs3-ps3-emulator-gets-cell-cpu-breakthrough-that-improves-performance-in-all-games)). Intel TSX support, once used for SPU reservations, was removed in November 2025; how 128-byte reservations are now handled was not documented in any source found ([Wikipedia: RPCS3](https://en.wikipedia.org/wiki/RPCS3); [RPCS3 PR #8721](https://github.com/rpcs3/rpcs3/pull/8721)). Vulkan is the recommended renderer. RSX vertex and fragment programs are decompiled to GLSL and then compiled to SPIR-V *(background)*.

PS3 static recompilation is the least mature of any PowerPC platform. **ps3recomp** lifts PPU code to C and extracts and lifts embedded SPU images. It models each SPU's local store, DMA and channels with per-image dispatch, provides native replacements for system libraries, and sends RSX command buffers to D3D12/Vulkan. Its own coverage lists synchronization, shader translation and per-game effort as open problems ([Generation Amiga](https://www.generationamiga.com/2026/06/15/ps3recomp-the-new-tool-bringing-native-playstation-3-ports-closer-to-pc/); [ps3recomp](https://github.com/sp00nznet/ps3recomp)). Saints Row 2 boots, runs its own SPU code and opens a D3D12 window. Scott Pilgrim hangs with an SPU task stuck in WAIT_SIGNAL and relies on a dump-on-miss mode that captures SPURS job images for later lifting ([saintsrow2](https://raw.githubusercontent.com/sp00nznet/saintsrow2/HEAD/README.md); [scottpilgrim](https://raw.githubusercontent.com/sp00nznet/scottpilgrim/HEAD/README.md)). This is the PS3's core obstacle to ahead-of-time translation: much SPU code is uploaded at runtime as jobs or overlays, so a pure AOT tool needs dump-and-lift loops or a JIT fallback.

### Xbox 360: eDRAM formats forced the most important ROV-vs-render-target study

The Xbox 360 is homogeneous. It has three big-endian PowerPC cores and the **ATI Xenos GPU: 48 unified 5-wide shader processors at 500 MHz (240 GFLOPS)**, plus a **10 MB eDRAM daughter die** with its own ROP logic for blend, Z and 4× MSAA ([Wikipedia: Xenos](https://en.wikipedia.org/wiki/Xenos_(graphics_chip))). Xenia's documentation explains why this is hard on PCs. The eDRAM uses tiles of 80×16 samples. A 720p target with 2× or 4× MSAA overflows 10 MB, so games use predicated tiling. The eDRAM also has formats PC GPUs lack: 7e3 "10.10.10.2" float, a ±32 fixed-point 16.16, piecewise-linear gamma, and **24-bit float depth**. The only way out of eDRAM is an explicit "resolve" copy or MSAA average into main memory ([Xenia, 2021](https://xenia.jp/updates/2021/04/27/leaving-no-pixel-behind-new-render-target-cache-3x3-resolution-scaling.html)). Shaders ship as Xenos microcode with reflection data ([XenosRecomp](https://github.com/hedge-dev/XenosRecomp)). Homebrew uses libXenon on RGH/JTAG hardware ([free60 LibXenon](https://free60.org/Development/LibXenon)).

Xenia's 2021 render-target cache rewrite is still the architecture, and it is the clearest public trade-off study of ROV versus conventional render targets. The **RTV path** keeps host render targets and performs bit-exact "ownership transfers" with generated pixel shaders whenever an eDRAM range changes format, pitch or sample count. It stores float24 depth rebiased to avoid D3D12 clamping. The **ROV path** encodes and decodes every eDRAM format in the pixel shader with no copies, which makes it the most accurate. The cost is lost hi-Z/early-Z and very long shaders, and it requires Maxwell 2nd generation or Vega and newer. On a GTX 1070, Halo 3 ran at **13.6 ms on RTV versus 23.8 ms on ROV**, and Banjo N&B at **17.5 ms versus 59.4 ms** ([Xenia, 2021](https://xenia.jp/updates/2021/04/27/leaving-no-pixel-behind-new-render-target-cache-3x3-resolution-scaling.html)). On Vulkan, the ROV equivalent depends on VK_EXT_fragment_shader_interlock, which AMD's RADV gained for GFX9 and newer via POPS ([Mesa POPS docs](https://docs.mesa3d.org/drivers/amd/hw/pops.html)). Older reports said interlock was nearly ineffective on Turing drivers ([NVIDIA forum](https://forums.developer.nvidia.com/t/windows-possible-driver-bug-fragment-shader-interlock-has-almost-no-effect-on-rtx-gpu-driver/79752)), and no 2024–26 quantitative comparison was found. Xenia Canary remains the active branch, with the Xenia Edge fork alongside it. Android ports (aX360e, XenDroid, X360 Mobile) build on Xenia's ARM64 backend ([Android Authority](https://www.androidauthority.com/ax360e-xbox-360-emulator-3625517/); [Generation Amiga](https://www.generationamiga.com/2026/08/19/xbox-360-emulation-gets-faster-on-android-with-xendroid/)). Specific Canary changes in late 2026 come from low-reliability sites *(unverified)*.

Static recompilation is mature here. **XenonRecomp** emits direct C++ on a full PPC register struct plus a base pointer, because guest pointers are 32-bit. It byte-swaps on load and store and marks all accesses `volatile`. It reverses whole 16-byte vectors rather than individual lanes, which permutes component order in some operations. It toggles flush-to-zero because the FPU keeps denormals while VMX flushes them. It finds functions from `.pdata` plus `bl` targets and pattern-matches jump tables into `switch` statements. Indirect calls go through a perfect hash, after an 8 GB lookup table caused memory pressure. It uses x86 intrinsics for VMX and SIMDe on ARM64 ([XenonRecomp](https://github.com/hedge-dev/XenonRecomp)). **XenosRecomp** is the GPU half, and it is directly relevant to ReGPU-V. It lifts Xenos shaders to HLSL, then uses DXC to emit **DXIL and SPIR-V**. Textures are bindless. Constants are root CBVs on D3D12 and push-constant buffer addresses read via `vk::RawBufferLoad` on Vulkan. Specialization constants handle alpha test and R11G11B10, and because **DXIL lacks specialization constants**, the DXIL path uses library linking with generated stubs. Output goes to an XXH3-keyed, zstd-compressed cache. The tool is explicitly tailored to one game ([XenosRecomp](https://github.com/hedge-dev/XenosRecomp)). Together they shipped Unleashed Recompiled (Sonic Unleashed) in 2025 ([Android Authority](https://www.androidauthority.com/xbox-360-recompiled-sonic-unleashed-3531514/)). In 2026 **ReXGlue** took Xenia's codebase wholesale, replaced the JIT with AOT PPC-to-C++ compiled by Clang, and kept Xenia's kernel and Xenos backend behind an abstract interface. Early ports include Blue Dragon, Lost Odyssey, Nuts & Bolts and Ninja Gaiden 2 ([readonlymemo interview](https://readonlymemo.com/rexglue-xbox-360-recompilation-interview/); [rexglue-sdk](https://github.com/rexglue/rexglue-sdk)). The cancelled 360 GoldenEye was also recompiled through it ([Tom's Hardware](https://www.tomshardware.com/video-games/retro-gaming/cancelled-xbox-360-version-of-goldeneye-007-gets-recompiled-for-pc-no-emulator-the-game-runs-as-a-real-native-executable-insists-dev)). Matching decomps remain rare and lean on leaked PDBs, such as the Bayonetta PDB and the prototype builds used by the NFS: Most Wanted decomp ([nfsmw](https://raw.githubusercontent.com/dbalatoni13/nfsmw/HEAD/README.md)).

## Eighth and ninth generations: native x86 shifts the problem to shader binaries

### Wii U: GameCube lineage on the CPU, a VLIW5 GPU to decompile

The Wii U's **Espresso is a tri-core PPC750-class CPU at about 1.24 GHz** with paired singles and no AltiVec. **Latte is an AMD R700/TeraScale VLIW5 GPU** with 32 MB of eDRAM, driven by the thin GX2 API, and games ship precompiled R700 shader microcode *(background, not re-verified)* ([wiiubrew Espresso](https://wiiubrew.org/wiki/Hardware/Espresso); [Latte](https://wiiubrew.org/wiki/Hardware/Latte)). Homebrew uses devkitPPC with wut and the Aroma environment ([wut](https://github.com/devkitPro/wut)). **Cemu**, open source under MPL-2.0 since 2.0, is mature. It recompiles PPC through an IML intermediate to x86-64, decompiles Latte microcode to GLSL and then SPIR-V for its primary Vulkan backend, and offers async shader compilation, transferable caches and graphics packs *(background)* ([Cemu](https://github.com/cemu-project/Cemu)). Stable 2.6 dates from February 2025. A claimed "2606" stable build and a report that 2.6's Linux release assets were swapped for malware in May 2026 both come from a single low-reliability site and are **unverified** ([tech-insider](https://tech-insider.org/how-to-set-up-cemu-wii-u-emulator-2026/)). Recompilation is emerging. **ZeldaWWHDRecomp v0.5.0 (29 October 2026)** runs Wind Waker HD natively on four OSes, with interpolated 60 fps ([XDA](https://www.xda-developers.com/the-zelda-wind-waker-hd-pc-port-ive-dreamed-of-finally-real-complete-with-buttery-smooth-60fps/)). CafeRecomp is trying to get Breath of the Wild past boot ([CafeRecomp](https://github.com/hardkiller2565123123/CafeRecomp)).

### PS4 and PS5: run the CPU natively, recompile GCN and RDNA shaders

The PS4 is an AMD APU. It has **8 Jaguar x86-64 cores at 1.6 GHz and an 18-CU GCN GPU sharing 8 GB of GDDR5**, running the FreeBSD-derived Orbis OS. The PS5 has a **Zen 2 CPU and a 36-CU RDNA2 GPU** with 16 GB of GDDR6 and hardware Kraken decompression *(background, not re-verified)* ([Wikipedia: PS4](https://en.wikipedia.org/wiki/PlayStation_4); [PS5](https://en.wikipedia.org/wiki/PlayStation_5)). Games program the GPU through GNM on PS4 and AGC on PS5. GNM writes raw **AMD PM4 command packets and register state**, and shaders ship as precompiled GCN or RDNA machine code, never portable IR ([shadPS4 video_core](https://github.com/shadps4-emu/shadPS4/tree/main/src/video_core); [GPCS4](https://github.com/Inori/GPCS4/blob/master/ReadMe.md)). That is why studio PC ports of PS4 games stutter: consoles ship finished ISA, while PCs must compile DXIL or SPIR-V.

**shadPS4 (GPLv2, Vulkan) reached v0.21.0 on 30 October 2026** ([shadPS4 releases](https://github.com/shadps4-emu/shadPS4/releases)). It runs PS4 x86-64 code natively. It resolves Sony's imports to HLE libraries or to firmware `.sprx` modules dumped by the user, and it patches the few places where "x86 is not quite x86". It emulates Jaguar's SSE4a `EXTRQ`/`INSERTQ` on Intel hosts, reproduces AMD's `RCPPS`/`RSQRTPS` lookup tables for bit-exact approximations, and rewrites `fs:[0]` TLS accesses for the FreeBSD ABI ([cpu_patches.cpp](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/cpu_patches.cpp)). Its shader recompiler, modelled on yuzu's Hades, is a template for any binary-shader translator. The frontend decodes GCN, parses GNM "fetch shaders" to infer vertex layouts, and structurizes EXEC-mask control flow. IR passes perform SSA repair, readlane and ballot elimination, **wave64 lowering for 32-wide hardware**, FP64-to-FP32 lowering, and discovery of V#/T#/S# resource descriptors in user SGPRs. A SPIR-V backend emits through `sirit` ([shader_recompiler](https://github.com/shadps4-emu/shadPS4/tree/main/src/shader_recompiler)). The `liverpool` command processor rebuilds Vulkan state from PM4 register writes, and a page manager tracks unified-memory coherence. Experimental GPU-to-CPU readbacks in v0.10.0 fixed Bloodborne's vertex explosions ([Wikipedia: ShadPS4](https://en.wikipedia.org/wiki/ShadPS4)). Digital Foundry measured Bloodborne at up to 60 fps in 4K on an RTX 4080 in January 2026 ([Wikipedia: ShadPS4](https://en.wikipedia.org/wiki/ShadPS4)). Later claims of 100+ fps are secondary ([Notebookcheck](https://www.notebookcheck.net/Bloodborne-PS5-remaster-fans-shouldn-t-keep-waiting-as-PS4-emulation-delivers-100-FPS-on-Ryzen-5-7600-and-RTX-5060.1329898.0.html)), and claims of ~200 fps with frame generation rest on a weak source *(unverified)*. A launch of shadNet online play in October 2026 is single-sourced ([Wccftech](https://wccftech.com/shadnet-playstation-4-emulation-shadps4-sidesteps-playstation-network/amp/)).

"Native ports" of PS4 games are not recompilations at all. **bbport** loads the retail Bloodborne executable in-process, reimplements the system functions it uses, and renders through a **Vulkan 1.3 renderer derived from shadPS4**, so only the CPU side is truly native ([Neoteo](https://www.neoteo.com/en/bloodbornes-unofficial-windows-build-runs-ps4-code-directly); [Mrsuss60 README](https://raw.githubusercontent.com/Mrsuss60/bloodborne_pc_windows_port/HEAD/README.md)). PS5 emulation went from nothing to early 3D between July and October 2026. **SharpEmu** (C#) reached gameplay in 12 of 55 tested games, 6 of them at 60 fps, all small titles ([Notebookcheck](https://www.notebookcheck.net/PS5-emulation-hits-new-milestone-SharpEmu-now-runs-six-games-at-60-FPS.1409228.0.html)). **KytyPS5** converts PS5 GPU programs to an IR, emits SPIR-V, and ran the PS5 GTA V at up to 60 fps before crashing ([Tom's Hardware](https://www.tomshardware.com/video-games/pc-gaming/ps5-emulator-can-now-run-the-console-version-of-gta-v-at-up-to-60-fps-on-pc-but-quickly-crashes-as-tweakers-continue-to-optimize-ps5-emulation-advancing-at-an-astronomical-pace-leading-up-to-gta-vi-launch)). The PS5 "Relapse" exploit that made dumps possible is reported only by secondary sources *(unverified)* ([cybersecuritynews](https://cybersecuritynews.com/ps5-relapse-exploit/)).

### Xbox One: "essentially a PC", yet still unemulated

The Xbox One has 8 Jaguar cores, a 12-CU GCN GPU, 8 GB DDR3 plus **32 MB of ESRAM** as a render-target scratchpad, and three OS partitions on a Hyper-V-derived hypervisor *(background, not re-verified)* ([Wikipedia: Xbox One](https://en.wikipedia.org/wiki/Xbox_One)). Games use D3D11.x/D3D12.x through the XDK and GDK, which are close to PC D3D12. Even so, **no working Xbox One emulator exists** ([Emulation General Wiki](https://emulation.gametechwiki.com/index.php/Xbox_One)). The only public effort is **XWine1**, a Wine-style translation layer announced in September 2024 with six playable games, which depended on dumps from the "Collateral Damage" kernel exploit. It remains unreleased according to the sources found ([Digital Trends](https://digitaltrends.com/gaming/xbox-one-emulation-xwine1/); [xboxoneresearch](https://xboxoneresearch.github.io/news/2024/08/15/news-recap.html)). A full solution would still need GCN-to-DXIL/SPIR-V translation or D3D12.x shimming, because console builds ship precompiled GCN shaders. A rumour of an official Microsoft x64 Xbox emulator rests on one leaker *(unverified)* ([Gameranx](https://gameranx.com/updates/id/538874/article/rumor-ms-is-making-an-xbox-emulator-on-windows-even-for-games-outside-the-backwards-compatibility-program/)).

### Switch: legal pressure scattered the emulators while recompilers surged

The Switch is a stock **Tegra X1: 4× Cortex-A57 for games and a 256-core Maxwell GM20B GPU**, with 4 GB LPDDR4 and the Horizon microkernel. Games use NVIDIA's proprietary NVN API, and shaders compile offline to Maxwell SASS *(background, not re-verified)* ([switchbrew Hardware](https://switchbrew.org/wiki/Hardware)). Homebrew uses libnx, deko3d (an open NVN-like API) and Atmosphère ([deko3d](https://github.com/devkitPro/deko3d); [Atmosphère](https://github.com/Atmosphere-NX/Atmosphere)). Emulators never implement NVN itself. They emulate below it: nvdrv ioctls, GPFIFO pushbuffers and the Maxwell 3D engine class, decoding SASS into an SSA IR that emits SPIR-V, GLSL or GLASM. CPU execution uses dynarmic or ARMeilleure JITs on x86 and native code execution (NCE) on ARM64 hosts *(background)* ([dynarmic](https://github.com/merryhime/dynarmic)).

Legally, the scene was gutted twice over. yuzu settled for **$2.4M** in March 2024. Ryujinx ended in October 2024 after an undisclosed "agreement" ([PC Gamer](https://pcgamer.com/software/nintendo-v-yuzu-switch-emulator-shut-down-settlement); [PC Gamer](https://pcgamer.com/gaming-industry/switch-emulator-ryujinx-goes-offline-after-creator-gets-an-offer-from-nintendo-they-cant-refuse)). In February 2026 a DMCA wave hit 13 forks ([Nintendo Life](https://www.nintendolife.com/news/2026/02/13-switch-emulators-hit-by-latest-wave-of-nintendo-takedowns)). On **17 August 2026 seven anti-circumvention notices removed 401 repositories** from GitHub in a day, a figure taken from a search summary ([GodisaGeek](https://godisageek.com/2026/08/nintendo-401-switch-emulator-repos-dmca/)). Eden, hosted off GitHub, is the most active survivor; Ryubing is in maintenance mode. Fork status beyond that comes from content-farm sites that contradict each other *(unverified)*.

Static recompilation filled the gap. **Power Moon Recomp** made Super Mario Odyssey 1.0.0 playable start to finish natively on Windows, Linux and macOS around 2–3 November 2026 *(secondary)* ([TweakTown](https://www.tweaktown.com/news/114465/super-mario-odyssey-native-pc-port-available-now-playable-from-start-to-finish-in-4k-at-60-fps/index.html)). **letsgo-recomp** translates Pokémon Let's Go's ARM64 to C, and its runtime replaces the kernel and services and maps NVN graphics to Vulkan. It builds on LASRecomp, which was made "almost exclusively with AI" ([XDA](https://www.xda-developers.com/pokemon-lets-go-switch-games-just-got-native-pc-ports-nintendo-probably-isnt-thrilled/)). **SwitchRECOMP** (AGPL-3.0) translates ExeFS ARM64 to C ahead of time, with a C runtime that emulates the "Maxwell GPU" through OpenGL or a Windows-only Vulkan renderer ([SwitchRECOMP](https://github.com/SwitchRECOMP-Dev/SwitchRECOMP)). Tracker listings of Mario Kart 8 Deluxe and Tears of the Kingdom recomps, and Suyu's claimed final release with a static-recompiler mode, are **unverified** ([pcport.org](https://pcport.org/en); [Wccftech](https://wccftech.com/nintendo-switch-emulation-leap-forward-suyu-native-pc-performance/)). Matching decomps such as OdysseyDecomp, reportedly around 15% at an undated point, use Nintendo's Clang-based toolchain and move slowly ([OdysseyDecomp mirror](https://github.com/Mars2032/odyssey)). No D3D12 backend was confirmed in any Switch emulator or recomp; all use Vulkan or OpenGL.

### Switch 2: a familiar OS on a new Ampere GPU, with emulation claims ahead of evidence

The Switch 2 uses NVIDIA's **T239: eight Cortex-A78C cores (six for games) and a 1536-CUDA-core Ampere GPU**, with Armv8.3 pointer authentication and memory encryption on some carveouts ([Switchbrew T239](https://switchbrew.org/wiki/Switch_2:_Tegra_T239)). Memory is 12 GB LPDDR5X with 9 GB for games ([TechPowerUp](https://www.techpowerup.com/336766/final-nintendo-switch-2-specifications-surface-cpu-gpu-memory-and-system-reservation)). Sources still conflict on its memory data rate (Switchbrew lists LPDDR5X-3750 at 120 GB/s; Geekerwan reports 8533-rated parts) and on which CPU clock belongs to which mode ([Nintendo Life](https://www.nintendolife.com/news/2025/05/nintendo-switch-2-final-tech-specs-have-been-confirmed); [Club386](https://www.club386.com/nintendo-finally-reveals-switch-2-specs-including-docked-and-handheld-clock-speeds/)). The OS architecture and user-mode AArch64 ISA carry over, so yuzu-lineage HLE transfers. The new work is an Ampere SASS decoder, new engine classes, PAC handling and heavier CPU load. **Lichii**, a GPL-3.0 Eden/Eglantine-derived fork, ships near-daily builds and self-reports Donkey Kong Bananza running and Mario Kart World at 30–38 fps on an M4 Pro. It uses **host DLSS through NVIDIA Streamline**, which implies it intercepts the game's DLSS dispatch at a high level ([lichii.org](https://lichii.org/)). All Switch 2 compatibility claims are **self-reported or from weak sources**, and one guide warns that many "Switch 2 emulator" sites are malware ([conservationctx](https://conservationctx.com/en/news/is-there-a-switch-emulator-current-state/)). No Switch 2 decomp or recomp exists, and no public documentation of Ampere SASS translation was found.

## DOS: no GPU to translate, so the GPU win depends on Glide or source code

DOS games program the hardware directly: CPU modes, VGA registers and the A000 framebuffer, Sound Blaster ports, the PIT timer, and BIOS/DOS interrupts. They cannot run natively on 64-bit Windows 11 or Linux. 64-bit Windows has no NTVDM, and long mode drops virtual-8086 mode. A 64-bit process cannot even modify its LDT, so otvdm runs 16-bit Windows code through CPU emulation rather than the native WOW subsystem ([otvdm/winevdm](https://github.com/otya128/winevdm)). Every route is therefore emulation, HLE of the hardware and OS interfaces, or a source port. A recompiled game still has to service INT 10h/16h/33h, VBE banking, DPMI real-mode calls, and a VGA register file that reads back what drivers wrote ([El-Fish recomp README](https://raw.githubusercontent.com/sp00nznet/elfish/HEAD/README.md)).

For playing, **DOSBox Staging 0.83.0 (27 August 2026)** is the polished choice. It adds authentic CRT colour emulation, VRR-aware frame presentation, wide-gamut support, a checkerboard "dedither", an FMV deinterlacer, Roland SC-55 emulation, and an HTTP API that exposes memory for modding tools ([GamingOnLinux](https://www.gamingonlinux.com/2026/08/dosbox-staging-0-83-brings-authentic-crt-colour-emulation-fmv-deinterlacer-disc-automounting-and-much-more/)). Its 3dfx Voodoo 1 emulation, inherited from MAME, is **software-only and does not translate Glide to a host API**. The modern GPU only scales and post-processes the result ([Staging 0.81.0 notes](https://www.dosbox-staging.org/download/release-notes/0.81.0/)). **DOSBox-X** (dated builds through 2026.08.31) is the only DOSBox route in which the host GPU rasterizes the game's 3D. Its `glide=true` pass-through exposes `GLIDE2X.OVL` to a host wrapper, but it works only for games that load Glide dynamically; statically linked titles must use low-level emulation ([DOSBox-X Voodoo guide](https://dosbox-x.com/wiki/Guide%3ASetting-up-3dfx-Voodoo-in-DOSBox%E2%80%90X)). **86Box v6.0 (May 2026)** emulates complete period PCs, including Voodoo 1/2/Banshee/3 and S3 ViRGE with multithreaded rendering, and it is the only option found for non-3dfx accelerated paths ([Linuxiac](https://linuxiac.com/86box-6-0-brings-big-update-to-the-retro-x86-emulator/); [86Box v5.3](https://86box.net/2025/12/21/86box-v5-3.html)).

The Glide wrappers are the true GPU-translation layer for DOS-era 3D. **nGlide** (closed source; Glide 2.11, 2.60 and 3.10) outputs to Vulkan or D3D9, and its Vulkan backend lets it run under Wine ([Emulation General Wiki: Wrappers](https://emulation.gametechwiki.com/index.php/Wrappers)). **dgVoodoo2** maps Glide 1–3 plus DirectDraw and D3D3–9 onto **D3D11/D3D12**. Its author has archived the GitHub repository and closed Linux/Wine reports ([dgVoodoo2](https://github.com/dege-diosg/dgVoodoo2)), and PCGamingWiki hosts community Wine/Proton-compatible builds ([PCGamingWiki](https://community.pcgamingwiki.com/files/file/3600-dgvoodoo2-v2793-v2813-wineproton-compatible/)). A newer Glide-to-Vulkan wrapper called "GXVK" was seen only as a headline *(unverified)* ([Hardware Busters](https://hwbusters.com/?p=121680)). Architecturally, Glide is a thin immediate-mode API taking pre-transformed screen-space vertices, with fixed-function colour and alpha combine units and app-managed texture memory. A wrapper therefore turns combine state into shader permutations, caches textures by TMU address, emulates linear-framebuffer access by readback and upload, and scales coordinates. That coordinate scaling is how a 640×480 Voodoo game renders at 4K.

Software-rendered DOS games only ever produce finished pixels, and no general project re-renders them at higher resolution. That path requires source, which is why released engines produced the best modern-GPU results: GZDoom's OpenGL/Vulkan renderers, vkQuake and Ironwail, EDuke32 and Raze for Build, DXX-Rebirth, and Shockolate *(project pages not re-fetched)* ([GZDoom](https://zdoom.org/); [vkQuake](https://github.com/Novum/vkQuake); [Raze](https://github.com/ZDoom/Raze)). Without source, three binary approaches work. **Spice86** (C#/.NET 10, Apache-2.0) runs a real-mode program, records its control-flow graph, and generates a C# project whose functions you override one by one. Cryo Dune is its reference case, and it does not support 286/386 protected mode ([Spice86](https://github.com/OpenRakis/Spice86)). **M-HT/SR** statically translates specific 32-bit DOS games (Albion, X-COM UFO and TFTD, Warcraft) to x86, ARM or LLVM IR, for targets from Windows x64 to Linux RISC-V, with scaler plugins ([M-HT/SR](https://github.com/M-HT/SR)). A 2025–26 wave of per-game 16-bit recomps follows N64Recomp's shape. El-Fish lifts about 15,213 functions to about 299K lines of C with a `recomp16` runtime, a flat memory image, and a VESA framebuffer presented as an SDL2 texture ([El-Fish README](https://raw.githubusercontent.com/sp00nznet/elfish/HEAD/README.md)). For analysis, Ghidra handles MZ natively but needs the third-party `ghidra-lx-loader` for DOS/4GW LE binaries, and one 2023 write-up found IDA more reliable for 16-bit code ([ghidra-lx-loader](https://github.com/oshogbo/ghidra-lx-loader); [Marco Guerri](https://marcoguerri.github.io/2023/08/26/reverse-engineering-msdos.html)). On Linux, Steam DOS titles run better through Boxtron or Luxtorpeda with native DOSBox Staging than through Proton wrapping the bundled Windows DOSBox ([Boxtron](https://www.github.com/dreamer/boxtron)). Win16 launchers on Windows 11 need otvdm or NTVDMx64 ([NTVDMx64](https://mendelson.org/ntvdmx64.html)).

## Common techniques: one CPU pattern, three GPU patterns

### Static recompilation is register-context code plus a reimplemented SDK

Every successful 2024–26 recompiler shares one design, whether it targets MIPS, PowerPC, ARM64, SH-4 or 16-bit x86. It translates each guest instruction literally into a statement on a context struct (`ctx->r4 = ADD32(...)` in N64Recomp and PS2Recomp, `c.T0 = ...` in RecompOne). It treats guest memory as one contiguous host allocation indexed by 32-bit offsets. It turns direct calls into host calls and jump tables into `switch` statements. It routes indirect calls through a lookup (N64Recomp's `LOOKUP_FUNC`, XenonRecomp's perfect hash) ([N64Recomp](https://github.com/N64Recomp/N64Recomp); [XenonRecomp](https://github.com/hedge-dev/XenonRecomp)). The generated code is deliberately unreadable. Modders patch it by overriding functions by symbol at link time, written against decomp headers, which lets recomp and decomp combine: recompile everything, decompile only what you change ([SED transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/09/SED1735-N64-Recomp.txt)). The per-platform work concentrates in a short list of hazards. These are function discovery when code and data mix (PS1), overlays and runtime-uploaded code (N64 overlays, PS3 SPURS jobs), endianness (whole-vector reversal on PPC), non-IEEE float semantics (PS2 COP1 clamping, SPU xfloat, PPC denormal toggling), and threading assumptions (one N64 game thread at a time). The runtime always **reimplements the SDK rather than the silicon**: libultra in N64ModernRuntime, PsyQ in Psy-X and PSY-Z, GX in Aurora, the Xbox 360 kernel in ReXGlue, Horizon services in Switch recomps. That is why SDK uniformity predicts platform maturity better than age does. Self-modifying code, TLB-mapped code and unresolved indirect branches remain the shared failure modes. None of the tools found handles them generally.

### HLE versus LLE is now a per-subsystem choice

The old binary of "fast HLE versus accurate LLE" has dissolved into hybrids chosen per subsystem. N64 recomps HLE the graphics microcode through RT64 but LLE the audio microcode by recompiling it ([Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)). shadPS4 HLEs most Sony libraries but loads dumped firmware modules for the rest ([shadPS4](https://github.com/shadps4-emu/shadPS4)). xemu emulates the whole Xbox while Cxbx-Reloaded intercepts its D3D8 ([xemu](https://github.com/xemu-project/xemu)). The deciding test for a renderer is what the target needs. LLE compute rasterizers (paraLLEl-RDP, paraLLEl-GS, Yaba Sanshiro's VDP1) give bit-faithful output at integer upscales but cannot do true widescreen or high frame rates. HLE draw translation (RT64, Fast3D, Aurora, Glide wrappers) enables arbitrary resolution, widescreen, interpolation and texture packs, but has to rebuild framebuffer effects heuristically. RT64's dual renderer, with a native-resolution RAM-synced pass alongside an upscaled replay, is the best published compromise ([RT64](https://github.com/rt64/rt64)).

### Fixed-function GPUs become uber-shaders, generated shaders or compute rasterizers

Translating a fixed-function GPU always comes down to three moves. The first is to hash the configuration (TEV stages, RDP combiner mux, GS TFX/blend bits, NV2A combiners, Glide combine state) into a shader key and generate specialized shaders, with an ubershader interpreting the same state as a fallback ([Dolphin](https://dolphin-emu.org/blog/2017/07/30/ubershaders/); [PCSX2](https://github.com/PCSX2/pcsx2)). The second is to model the console's memory, rather than its API objects, with a texture cache that resolves format aliasing: GS pages reread as other formats, Xenos eDRAM ownership transfers, PS1 VRAM CLUTs, N64 framebuffers read as textures. The third is to handle blending the host cannot express in fixed-function hardware. Above-1.0 alpha, destination-dependent factors, PowerVR2 translucency sorting and custom eDRAM formats need either a render-target copy or barrier per primitive, **ROVs (D3D12) or fragment-shader interlock (Vulkan)**, or a full compute rasterizer with explicit hazard tracking, as in paraLLEl-GS ([themaister](https://themaister.net/blog/2024/07/)). Xenia's measurements show ROV costing 1.7–3.4× the render-target path on a GTX 1070, which is why it ships as an option rather than a default ([Xenia, 2021](https://xenia.jp/updates/2021/04/27/leaving-no-pixel-behind-new-render-target-cache-3x3-resolution-scaling.html)). PCSX2's 2026 adoption of ROV on its D3D12 default path suggests the calculation has shifted on current GPUs, though no modern benchmark confirms it ([gaming-st.com](https://gaming-st.com/news/pcsx2-2-8-direct3d12-release/)). For shader-binary consoles (Xenos, GCN, RDNA, Maxwell, R700), the pattern is decoder → SSA IR → structurization → SPIR-V, optionally via HLSL and DXC to reach DXIL. XenosRecomp and shadPS4 are the two best public references.

### Shader stutter is solved by interpreting first and specializing later

Every project here that took stutter seriously landed on the same layered answer that ReGPU-V's earlier Vulkan research reached for native renderers: persisted pipeline caches, then graphics pipeline library fast-linking, then explicit enumeration of the pipeline set ahead of time, with "uber-shader first, specialize later". Dolphin's hybrid ubershaders draw immediately and swap in specialized pipelines compiled in the background ([Dolphin](https://dolphin-emu.org/blog/2017/07/30/ubershaders/)). RT64 uses ubershaders specifically to avoid D3D12/Vulkan PSO-compile stutter ([RT64](https://github.com/rt64/rt64)). Aurora ships **transferable pipeline caches** recorded during play, the source-port equivalent of Unreal's PSO precaching ([Aurora](https://github.com/encounter/aurora)). paraLLEl-RDP keeps the shader count small by specializing a handful of SPIR-V modules through specialization constants ([libretro](https://www.libretro.com/?p=48552)). XenosRecomp precompiles every shader offline into a hashed cache, and it shows a portability trap: DXIL has no specialization constants, so the D3D12 path needs library linking instead ([XenosRecomp](https://github.com/hedge-dev/XenosRecomp)). Static recompilation has an advantage over emulation here, because the shader set of one game is finite and can be enumerated at build time, the same advantage Aurora's per-release caches exploit.

## What this means for ReGPU-V

The research points to a concrete shape for a GPU translation layer that targets Vulkan and D3D12 together. Start the shader path from HLSL or an SSA IR and go through DXC (or Slang) to both DXIL and SPIR-V, as XenosRecomp does. Use bindless resources and buffer-address constants to avoid descriptor permutations. Keep fixed-function state on the pipeline-key side, with an interpreting ubershader for unseen keys. Treat ROV and fragment-shader interlock as a first-class *accuracy tier* rather than the default. Xenia's data and PCSX2's 2026 shift both say this tier is affordable now, but its value depends on the vendor. RADV supports interlock on GFX9+, and NVIDIA's historical interlock performance was poor ([Mesa POPS](https://docs.mesa3d.org/drivers/amd/hw/pops.html)). Budget for a compute-rasterizer escape hatch where a guest GPU's raster rules cannot be expressed as triangles (Saturn VDP1, N64 coverage, PS2 GS feedback loops). Design the memory model around a guest-address texture and render-target cache with format aliasing and readback, because every console from the PS1 to the PS4 needed one. Licensing matters for reuse. RT64, Aurora, libultraship and SR are MIT. Spice86 is Apache-2.0 and Cemu is MPL-2.0. PCSX2 and N64ModernRuntime are GPL-3, and shadPS4 and xemu are GPL-2.0. DuckStation's CC-BY-NC-ND forbids derived work ([RT64](https://github.com/rt64/rt64); [Aurora](https://github.com/encounter/aurora); [N64ModernRuntime](https://github.com/N64Recomp/N64ModernRuntime); [DuckStation](https://github.com/stenzek/duckstation)).

## Legal lines run through keys, trademarks and distribution, not emulation itself

US precedent from *Sony v. Connectix* (2000) treats reverse engineering a BIOS to build an emulator as fair use *(background)* ([Wikipedia](https://en.wikipedia.org/wiki/Sony_Computer_Entertainment,_Inc._v._Connectix_Corp.)). Enforcement in 2024–26 has targeted three other things. The first is **circumvention**. Nintendo's yuzu complaint centred on decryption with prod.keys and ended in a $2.4M consent judgment, and the 2026 GitHub takedowns used DMCA §1201 anti-circumvention notices ([PC Gamer](https://pcgamer.com/software/nintendo-v-yuzu-switch-emulator-shut-down-settlement); [GodisaGeek](https://godisageek.com/2026/08/nintendo-401-switch-emulator-repos-dmca/)). The second is **active platforms**. The Switch forks were hit while Wii U's Cemu has faced no action found. The third is **trademarks and distribution**. Sony's agent sent a DMCA notice against Lance McDonald's Bloodborne 60 fps patch, which McDonald attributed to the "Bloodborne" name rather than the patch itself, while shadPS4 has faced no action found ([PC Gamer](https://pcgamer.com/games/action/sony-bullies-bloodborne-60fps-mod-off-the-internet-with-dmca-takedown-as-it-continues-to-let-the-fromsoft-classic-gather-dust-on-ps4); [Push Square](https://pushsquare.com/news/2025/01/sony-issues-dmca-takedown-against-bloodborne-60fps-mod-four-years-after-release)). Recompilers and decomp ports uniformly ship no game data, BIOS, keys or firmware, and require the user's own dumps. OpenPete even withholds its repository because it contains copyrighted validation data ([RecompOne](https://raw.githubusercontent.com/BlackLabelHQ/RecompOne/HEAD/README.md); [Time Extension](https://www.timeextension.com/news/2026/08/ps1-classic-spyro-the-dragon-comes-to-pc-with-the-help-of-ai-assisted-tool-psxrecomp)). Matching decomps distribute code derived from copyrighted binaries, and that remains **untested in court**. No action against a decomp or recomp project was found as of November 2026. A Switch recompiler that decrypts NCAs itself would plausibly carry the same §1201 exposure as an emulator. Separately, in October 2026 decomp.dev closed its public index, saying "the community aspect of decompilation has been broken" by AI-driven drive-by contributions ([Time Extension](https://www.timeextension.com/news/2026/10/the-community-aspect-of-decompilation-has-been-broken-decomp-dev-closes-in-the-wake-of-ai-based-bad-actors)). Projects now split along AI-disclosure lines: RecompOne and Zelda64Recomp ban generated contributions, while Red Two, Mario Kart Wiicompiled and LASRecomp were built with it.

## Conclusion

Two shifts change how this field should be understood. The first is that static recompilation has become a commodity. Once N64Recomp proved the register-context-plus-runtime pattern, it took one or two years to reach the PS1, Xbox 360, GameCube, Wii, Wii U and Switch. AI coding assistants then compressed per-game effort to weeks, Red Two going from first commit to v1.0 in thirteen days. That speed moves the bottleneck entirely onto the runtime, and above all the renderer, which is why so many 2026 ports quietly reuse a few graphics layers: RT64, Aurora, Xenia's Xenos backend, shadPS4's GCN recompiler. The second shift is that native ports have not escaped emulation on the GPU side; they have relocated it. bbport is native x86 feeding an emulated GCN, and ReXGlue is AOT PowerPC feeding Xenia's eDRAM model. The durable engineering value therefore lies in a reusable, Vulkan- and D3D12-native translation layer for console GPU semantics. That means an aliasing texture cache, ubershader-plus-cache pipelines, an ROV/interlock accuracy tier and a compute-rasterizer fallback, which is precisely the territory a project like ReGPU-V occupies.

The weakest links in current knowledge are worth naming. No primary write-up explains how any 2026 GameCube, Wii, Switch or PS1 recompiler structures its GPU backend. ROV versus render-target cost has not been measured on RDNA3/4, Ada/Blackwell or Arc. Switch 2 emulation status rests almost entirely on self-reports. And the PS2 and PS3 remain gated by per-game vector microcode that no one has yet translated to GPU compute. Whoever solves VU1 and SPU translation generically, or publishes the GPU-backend designs the 2026 recomps left undocumented, will set the next template.
