# Port to Vulkan 1.3, accelerate with 2026 extensions

A renderer engineer porting to Vulkan in late 2026 should **target Vulkan 1.3 with Roadmap 2022 features as the hard floor, treat Vulkan 1.4 / Roadmap 2024 as the preferred tier, and use the 2025–2026 extensions (descriptor heap, unified image layouts, pipeline binary, present timing) as detected fast paths.** No Vulkan 1.5 exists. Vulkan 1.4 (Dec 2024) is still the newest core version, and new capability now arrives as extensions gathered into the Roadmap 2026 profile. The biggest change for anyone coming from Direct3D 12 is **VK_EXT_descriptor_heap (January 2026)**. It deliberately mirrors D3D12 descriptor heaps, so a bindless, D3D12-shaped backend now maps almost one-to-one onto Vulkan on NVIDIA and current Mesa drivers. It reaches only about 28% of gpuinfo Windows reports, though, so a descriptor-indexing bindless path stays mandatory as the baseline. The rest of the 2026 picture is consistent. Performance comes from suballocated memory, batched sync2 barriers derived by a render graph, GPU-driven indirect drawing, and pipelines compiled before draw time. Linux presentation (Wayland FIFO, present timing, HDR, explicit sync) has largely caught up with Windows. Shader toolchains have settled on DXC for HLSL shared with D3D12 and Slang for new or multi-target code. For ReGPU-V, the lowest-risk path is to modernize the D3D12 backend first (enhanced barriers, SM6.6 bindless), extract a thin D3D12-shaped RHI, and bring Vulkan up beside it with image-diff testing against the D3D12 reference.

## Vulkan 1.4 is still current; Roadmap 2026 defines the high end

Vulkan 1.3 (January 2022) is the release that made Vulkan pleasant. It promoted **dynamic rendering, synchronization2, extended dynamic state, maintenance4, inline uniform blocks and subgroup size control** into core, and made dynamicRendering, synchronization2 and maintenance4 mandatory ([Vulkan spec, Core Revisions](https://docs.vulkan.org/spec/latest/appendices/versions.html)). Timeline semaphores, buffer device address, descriptor indexing and scalar block layout had already reached core in 1.2. Together these remove the VkRenderPass/VkFramebuffer boilerplate and the binary-semaphore-only frame sync that made early Vulkan code so verbose.

Vulkan 1.4 (December 2024) promoted **push descriptors, maintenance5 and 6, load_store_op_none, line rasterization, vertex attribute divisor, uint8 indices, map_memory2, global priority and pipeline robustness**. It also raised guaranteed limits: 8 color attachments, 7 bound descriptor sets, 256-byte push constants and 8192 image dimensions ([Vulkan 1.4 proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_VERSION_1_4.html)). Two partial promotions matter for porting. **dynamic_rendering_local_read** requires only color and storage local reads, with depth/stencil and multisampled local reads optional. **host_image_copy** is promoted but optional, since a 1.4 device must provide either it or an extra transfer-capable queue for streaming. SDK 1.4.304.0 (January 2025) was the first with full 1.4 support, and Mesa's NVK was conformant on day zero ([LunarG](https://www.lunarg.com/lunarg-releases-vulkan-sdk-1-4-304-0-full-support-for-vulkan-1-4); [GamingOnLinux](https://gamingonlinux.com/2024/12/vulkan-api-14-released-with-new-required-extensions-better-8k-rendering)).

Since then, features have arrived as extensions. Three post-1.4 additions change backend design. **VK_KHR_unified_image_layouts** (June 2025) lets VK_IMAGE_LAYOUT_GENERAL be used almost everywhere without a performance penalty, so barriers carry only memory dependencies. UNDEFINED (for discard) and the PRESENT layouts survive, and some hardware still wants GENERAL→GENERAL image barriers ([proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_KHR_unified_image_layouts.html)). **VK_EXT_descriptor_heap** shipped in Vulkan 1.4.340 on 23 January 2026, with NVIDIA, AMD, Arm, Nintendo, Valve and Google contributing ([Khronos blog](https://www.khronos.org/blog/vulkan-introduces-roadmap-2026-and-new-descriptor-heap-extension)). Maintenance extensions 7 through 12 have also shipped. Maintenance11 (May 2026) adds D3D-compatibility for arrayed-ness mismatches between shaders and descriptors, and maintenance12 arrived in Vulkan 1.4.367 in late October 2026 ([maintenance11 proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_KHR_maintenance11.html); [Phoronix](https://phoronix.com/news/Vulkan-1.4.367)). The research did not retrieve the contents of maintenance7, 8 or 12. No source confirms or rules out a Vulkan 1.5, and nothing at SIGGRAPH 2026 announced one.

The **Roadmap profiles** are the practical definition of "safe" hardware, because core versions alone guarantee little. Roadmap 2022 requires 1.3 plus full descriptor indexing (runtime arrays, update-after-bind, non-uniform indexing, variable counts). Roadmap 2024 adds push descriptors, local read, maintenance5, multiDrawIndirect, shaderDrawParameters and 8/16-bit types. Roadmap 2026, published 23 January 2026, requires 1.4 plus **robustness2, pipeline_binary, fragment shading rate, cooperative matrix, maintenance7–9, shader_untyped_pointers, present_wait2/present_id2, swapchain_maintenance1, hostImageCopy and nullDescriptor** ([Spec Roadmap appendix](https://docs.vulkan.org/spec/latest/appendices/roadmap.html)). Khronos expects most adopters to ship Roadmap 2026 devices by the end of 2026, and SDK 1.4.341.0 ships the profile ([LunarG](https://www.lunarg.com/lunarg-releases-vulkan-sdk-1-4-341-0/)). The Vulkan Profiles layer can simulate any of these profiles on a more capable GPU, which is the cheapest way to test that the engine really runs on its declared baseline ([Vulkan-Profiles](https://github.com/KhronosGroup/Vulkan-Profiles)).

Fleet data argues for caution with the newest items. On gpuinfo Windows reports, **timeline semaphores reach 92.8%, push descriptors 91.7% and synchronization2 87.9%**. Graphics pipeline library and extended_dynamic_state3 sit near 72%, shader objects at 57%, pipeline_binary at 53.5%, mesh shaders at 49% and ray tracing pipelines at 51%. Maintenance9, unified layouts and present_wait2 fall to **31–38%** ([gpuinfo](https://vulkan.gpuinfo.org/listextensions.php?platform=windows)). These numbers count device reports, including old GPUs and stale drivers, so they understate support on current hardware. They still show that anything newer than about 2024 must be optional.

| Tier | Requirement | Use for |
|---|---|---|
| Floor | Vulkan 1.3 + Roadmap 2022 + robustness2 + push descriptors + mutable descriptors | Dynamic rendering, sync2, timeline semaphores, bindless descriptor indexing, BDA |
| Preferred | Vulkan 1.4 / Roadmap 2024 | Push descriptors in core, local read, maintenance5/6, 8/16-bit types, MDI |
| Fast paths (detect) | descriptor_heap, unified_image_layouts, pipeline_binary, GPL / shader_object, present_timing / present_wait2, device_generated_commands | D3D12-like binding, layout-free barriers, explicit binary caches, pacing, state-changing indirect |
| Capability tiers | mesh shaders, ray tracing, cooperative matrix, VRS | Features with fallbacks |
| Avoid investing | descriptor_buffer (new work), AMDX work graphs, VK_NV_mesh_shader, secondary command buffers as a threading tool | Superseded, provisional or vendor-specific |

## Descriptor heaps make Vulkan binding D3D12-shaped

Binding has always been the hardest part of mapping D3D12 onto Vulkan, and it has now gone through four generations. Classic **descriptor sets** need layouts, pools and per-set allocation. **Descriptor indexing** (core 1.2, required by Roadmap 2022) enables one large global bindless set. **VK_EXT_descriptor_buffer** gave applications control of descriptor memory but kept the set/layout model. **VK_EXT_descriptor_heap** removes sets, pools and layouts entirely. The application writes descriptors into app-allocated memory with `vkWriteResourceDescriptorsEXT`, then binds one resource heap and one sampler heap with `vkCmdBindResourceHeapEXT` and `vkCmdBindSamplerHeapEXT`. Khronos recommends binding them once for the application's lifetime, because rebinding is expensive ([NVIDIA Technical Blog, June 2026](https://developer.nvidia.com/blog/streamlining-resource-binding-with-end-to-end-support-for-vulkan-descriptor-heaps/)). NVIDIA describes the model as one D3D12 developers will find familiar. The differences are that Vulkan lets the app choose the exact memory location of the heap, and descriptor sizes vary by type. Existing set/binding shaders run unchanged through `VkShaderDescriptorSetAndBindingMappingInfoEXT`. Direct heap indexing from shaders, the analogue of SM6.6 `ResourceDescriptorHeap`, needs VK_KHR_shader_untyped_pointers and is described as "still maturing" in toolchains.

Driver support moved fast on Linux and NVIDIA. NVIDIA supports descriptor heap from the R595 branch, with driver 610 and Nsight Graphics 2026.2 providing full tooling. RADV merged it in Mesa 26.1 behind an experimental flag and turned it on by default in 26.2, Intel ANV has experimental support, and vkd3d-proton and DXVK 3.0 already use it ([Phoronix RADV](https://phoronix.com/news/RADV-Descriptor-Heap-Default); [Phoronix ANV](https://phoronix.com/news/intel-anv-descriptor-heap-merge); [Phoronix vkd3d-proton](https://phoronix.com/news/vkd3d-proton-descriptor-heaps)). The research found no status for AMD's Windows Adrenalin driver, and **no published performance comparison between heap, buffer and set models**. The descriptor_heap proposal says descriptor_buffer's performance portability was "lower than ideal", and that reading descriptors back from device-local or uncached memory on the host is catastrophic ([descriptor_heap proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_descriptor_heap.html)). That is enough reason to skip new descriptor_buffer work, though Themaister still calls it a sound middle ground for CPU savings in his March 2026 Granite port ([Themaister](https://themaister.net/blog/2026/03/)). Tooling has caught up. SDK 1.4.341.0 added CPU validation for heaps, and SDK 1.4.357.0 (July 2026) extended GPU-assisted validation to descriptor_heap and descriptor_buffer and added a GPU Dump tool for debugging descriptors ([LunarG 1.4.357.0](https://lunarg.com/lunarg-releases-vulkan-sdk-1-4-357-0/)).

The recommended design has two tiers. The baseline, which runs on every Roadmap 2022 desktop device, is a single global bindless set (update-after-bind, partially bound, variable count) for textures and samplers, with buffer device addresses passed in push constants for buffers. Push descriptors or push constants carry per-draw data. The fast path is descriptor heap where the device exposes it. Both tiers present the same "index into a global table" model to shaders, so the shader source does not fork. Mobile remains the exception, where classic descriptor sets with modest counts are still safest ([Samsung](https://developer.samsung.com/game/usage)).

## A D3D12 renderer ports cleanly once its barriers and binding are modern

Most D3D12 concepts have direct Vulkan counterparts, and the Vulkan Guide's "decoder ring" gives the official mapping. A command list is a command buffer, a command allocator a command pool, a **D3D12 fence a timeline semaphore**, a root signature a pipeline layout, a descriptor table a descriptor set, a PSO a VkPipeline, and a resource barrier a pipeline barrier. VkImageView covers RTV, DSV, SRV and UAV alike ([Vulkan Guide: Decoder Ring](https://docs.vulkan.org/guide/latest/decoder_ring.html)). The ring leaves out several mappings, which follow standard practice. Root constants become push constants. Root CBV/SRV/UAV descriptors become push descriptors (core in 1.4) or buffer device addresses. Static samplers become immutable samplers. A committed resource becomes a dedicated allocation, and a placed resource becomes `vkBind*Memory` at an offset into a VMA-suballocated block. UPLOAD heaps map to ReBAR DEVICE_LOCAL|HOST_VISIBLE memory, as vkd3d-proton does, and READBACK heaps to HOST_CACHED memory. D3D12 has no mandatory render-pass object, so Vulkan 1.3 dynamic rendering is the natural match.

**Barriers are where a port succeeds or bleeds time.** Legacy D3D12 resource states bundle layout, cache access and synchronization into one enum. Microsoft's own spec calls implicit promotion and decay "a major source of developer confusion". D3D12 Enhanced Barriers split each barrier into Sync, Access and Layout, remove promotion and decay, and support split barriers ([D3D12 Enhanced Barriers spec](https://microsoft.github.io/DirectX-Specs/d3d/D3D12EnhancedBarriers.html)). That triple maps almost field-for-field onto `VkImageMemoryBarrier2` stage, access and layout masks. NVIDIA's NRI demonstrates the point by sitting a single barrier API over D3D12 Enhanced Barriers and Vulkan synchronization2 ([NRI](https://github.com/NVIDIA-RTX/NRI)). A renderer still on legacy states should migrate its D3D12 backend to enhanced barriers before writing any Vulkan code. Doing so converges the two backends' barrier logic and exposes latent sync bugs while the D3D12 debug layer is still available.

**Indirect execution** splits by complexity. ExecuteIndirect with only draw or dispatch arguments maps to `vkCmdDrawIndexedIndirectCount` and `vkCmdDispatchIndirect`. ExecuteIndirect that changes root parameters needs **VK_EXT_device_generated_commands**, which the Vulkan proposal describes as matching D3D12's expressivity and going beyond it, since it can also switch shaders from the GPU ([EXT DGC proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_device_generated_commands.html)). vkd3d-proton needed NVIDIA's DGC extensions to run Starfield, whose ExecuteIndirect "hammers multi-dispatch COMPUTE + root parameter changes" ([GamingOnLinux](https://gamingonlinux.com/2023/09/vkd3d-proton-v2-10-various-game-fixes-directstorage/page=1)). Limiting ExecuteIndirect to plain draws and dispatches where possible keeps the port on the portable path.

Smaller pitfalls are well known. Vulkan clip space has +Y pointing down, which is fixed with a negative-height viewport (core since 1.1) or DXC's `-fvk-invert-y`, while depth range [0,1] matches D3D ([Vulkan spec](https://docs.vulkan.org/spec/latest/chapters/vertexpostproc.html)). Typeless DXGI formats become a concrete VkFormat with MUTABLE_FORMAT and a format list ([formats](https://docs.vulkan.org/spec/latest/chapters/formats.html)). Undefined behavior that D3D12 drivers tolerate, such as out-of-bounds descriptor access, needs robustness2 with nullDescriptor to behave the same way in Vulkan, which is why vkd3d-proton makes it mandatory.

**vkd3d-proton is a production existence proof** that all of D3D12 maps onto Vulkan 1.3, and its requirements make a sensible floor for a native port. It needs Vulkan 1.3; descriptor indexing with at least **1,000,000 update-after-bind descriptors**; samplerMirrorClampToEdge; shaderDrawParameters; robustness2; and push descriptors. It recommends mutable descriptor types (created by Valve engineers so that one set can replace six for the CBV/SRV/UAV heap) and descriptor buffer, and it now uses descriptor heap. Its minimum recommended drivers are NVIDIA 595+ and Mesa 26.1+ ([vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton)). Its history confirms where the difficulty lies. Binding drove every extension it championed, and descriptor buffer support alone reportedly removed "a ton of CPU overhead" ([linuxcompatible](https://www.linuxcompatible.org/story/vkd3dproton-28-released/)).

On abstraction layers, a thin explicit RHI preserves the D3D12 renderer's design best. **NRI** (MIT) targets D3D12 with enhanced barriers, Vulkan 1.4, Metal and others, deliberately omits automatic barriers, and its authors report NVRHI costing **3–8× more CPU** than NRI in their workloads. That figure is the vendor's own and has not been independently measured ([NRI](https://github.com/NVIDIA-RTX/NRI)). NVRHI adds automatic barriers and lifetimes, which is convenient but costs CPU ([NVIDIA blog](https://developer.nvidia.com/blog/writing-portable-rendering-code-with-nvrhi)). SDL3 GPU lacks ray tracing, and WebGPU-style layers lack a bindless baseline, so both fit a bindless, ExecuteIndirect-heavy renderer poorly ([SDL3 GPU wiki](https://wiki.libsdl.org/SDL3/CategoryGPU)). The case-study record is thin but cautionary. Larian added Vulkan to Baldur's Gate 3 because of the Stadia deal, with a team that had little Vulkan experience, so issues went unnoticed for long stretches and the path shipped labelled Early Access ([80.lv](https://80.lv/articles/baldur-s-gate-3-dev-explained-why-it-supports-two-apis); [Larian FAQ](https://larian.com/support/faqs/what-is-vulkan-what-is-the-difference-between-vulkan-and-dx11_48)). Godot found that an RHI coupled too tightly to Vulkan leaked into the engine, and it fixed this with an acyclic render graph that derives barriers automatically ([Godot](https://godotengine.org/article/rendering-acyclic-graph/)). No public data exists on person-months for a D3D12-to-Vulkan port.

## Performance comes from memory, barriers and pipelines, not draw-call tricks

Vendor guidance agrees on the fundamentals. **Suballocate from large blocks.** AMD suggests 256 MB heaps, and VMA is the de facto standard. Keep usage near **80% of the VK_EXT_memory_budget budget**, and pick a memory type that is actually DEVICE_LOCAL rather than the first one listed ([AMD RDNA guide](https://gpuopen.com/learn/rdna-performance-guide/); [NVIDIA Dos and Don'ts](https://developer.nvidia.com/blog/vulkan-dos-donts/)). Give render targets dedicated allocations with priority 1.0, created before textures and meshes ([VMA usage patterns](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/usage_patterns.html)). Use ReBAR memory only for small, sequentially written, CPU-to-GPU data. It is write-combined, so a read-modify-write such as `ptr[i] += v` is a trap, and without ReBAR the BAR window is only about 256 MB. VMA's ALLOW_TRANSFER_INSTEAD flag builds in the automatic staging fallback. Stream through the dedicated transfer queue, synchronized with timeline semaphores. Alias transient render targets, but fully initialize each alias with a clear, discard or copy, or you risk hangs and corruption.

**Synchronization should be batched, precise and generated.** NVIDIA, AMD and Intel all say to batch barriers into one `vkCmdPipelineBarrier2`, use the narrowest stage and access masks, use UNDEFINED as the old layout when contents don't matter, and drop read-to-read barriers. Use split barriers via events where the gap allows ([NVIDIA](https://developer.nvidia.com/blog/vulkan-dos-donts/); [Intel Arc guide](https://www.intel.com/content/www/us/en/developer/articles/guide/arc-a-series-gaming-api-developer-optimization.html)). Within a queue, use barriers rather than semaphores, and use semaphores only across queues. Themaister's rules for correctness still hold. Command buffer and submit boundaries add no implicit sync, READ flags never belong in srcAccessMask, and fences do not make data visible to the host without a HOST_READ barrier ([Themaister](https://themaister.net/blog/2019/08/14/yet-another-blog-explaining-vulkan-synchronization/)). Getting barriers right everywhere requires knowledge of the whole frame, which is why a **render graph** is standard. O3DE, Blender and Godot all generate barriers, aliasing, layout transitions and queue-ownership transfers when the graph is compiled ([O3DE, Vulkanised 2024](https://dev.vulkan.org/user/pages/09.events/vulkanised-2024/vulkanised-2024-akio-gaule-o3de.pdf); [Blender](https://developer.blender.org/docs/features/gpu/vulkan/barrier_management/)). Unified image layouts slot into such a graph as a mode that collapses layout tracking to GENERAL plus memory barriers. Note that AMD's older advice to avoid GENERAL predates that extension, so keep the layout-tracking path as a fallback.

**Command recording** guidance favors big primaries. Use L×T+N command pools (buffered frames × recording threads, plus extras), reset pools instead of freeing buffers, submit rarely, and give each command buffer at least 10 draws ([NVIDIA](https://developer.nvidia.com/blog/vulkan-dos-donts/); [AMD](https://gpuopen.com/learn/rdna-performance-guide/)). **AMD and Intel both advise against secondary command buffers**, while NVIDIA tolerates them. On AMD, keep root data under about 13 DWORDs: a set costs 1 DWORD, push constants 1 per 4 bytes, and a dynamic buffer 2 (4 with robust access). The broader 2025–2026 direction is GPU-driven rendering, with bindless or heap descriptors, GPU culling, and a few `vkCmdDrawIndexedIndirectCount` calls per pass. This shrinks CPU recording cost enough that multithreaded recording matters less than it did in 2016-era designs ([Vulkan-Samples](https://docs.vulkan.org/samples/latest/samples/performance/README.html)).

**Render-pass hygiene** is nearly free on every vendor and decisive on tilers. Arm measured LOAD_OP_CLEAR with STORE_OP_DONT_CARE cutting external reads by up to **36%** and writes by up to **62%**. Merged deferred subpasses saved 45% of read and 56% of write bandwidth because the G-buffer never touched DRAM ([Arm](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/vulkan-samples)). On desktop, AMD fast clears run about 100× faster than normal clears but need full-image clears to specific colors (0 or 1 per channel) and depth 0.0 or 1.0. STORAGE usage on render targets can disable compression on AMD and Intel ([AMD](https://gpuopen.com/learn/rdna-performance-guide/)). On AMD, D32 with reversed-Z costs the same as 24-bit depth. NVIDIA prefers D24S8 or D32_SFLOAT over D32_S8, and flipping the depth comparison direction mid-frame disables Z-cull. **Async compute** pays off next to geometry-bound work such as shadows and depth prepass, and hurts next to export-bound shaders, so make it a per-pass render-graph toggle enabled per vendor after profiling. NVIDIA warns that pre-Ampere GPUs can show execution gaps ([NVIDIA](https://developer.nvidia.com/blog/vulkan-dos-donts/)).

The vendors disagree in three places a cross-vendor engine must handle. Secondary command buffers are tolerated by NVIDIA and discouraged by AMD and Intel. CONCURRENT sharing is free on NVIDIA but AMD advises against it on render targets. The value of async compute depends on the architecture. For measurement, keep debug-utils labels in release builds, lock clocks, and never profile with validation enabled. Use Nsight Graphics/Systems, RGP/RMV and GPA for deep dives, and per-pass GPU timestamps for always-on breakdowns. No vendor publishes a numeric cost per barrier or a benchmark of draws per second for MDI-count, so the advice above is qualitative.

## Shader compilation is solved by knowing your pipelines before draw time

For a renderer that shares HLSL with D3D12, **DXC `-spirv` is the standard path**, but its defaults bite. `register(xN, spaceM)` maps to binding N in set M and ignores the register class, so t0, b0 and s0 collide. Fix this with `-fvk-{b,t,s,u}-shift` (for example b+0, t+1000, s+2000, u+3000), `[[vk::binding]]` attributes, or `-fvk-auto-shift-bindings`. Default buffer layout is std140/std430, not D3D cbuffer packing, so use `-fvk-use-dx-layout` (needs scalar block layout, core in 1.2). `-fspv-target-env` defaults to vulkan1.0, which rejects wave intrinsics. `-fvk-support-nonzero-base-instance` reproduces D3D's SV_InstanceID semantics ([DXC SPIR-V.rst](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/SPIR-V.rst)). SM6.6 `ResourceDescriptorHeap` has two paths. An emulated path uses descriptor indexing plus mutable descriptors. A native path, `-fspv-use-descriptor-heap`, emits SPV_EXT_descriptor_heap and needs untyped pointers and vulkan1.3, and it does not support append/consume buffers or UAV counters. SPIR-V support is **partial for SM6.5, 6.6 and 6.7** ([Vulkan Guide: HLSL](https://docs.vulkan.org/guide/latest/hlsl.html)), and the research did not confirm the SM6.8/6.9 status (work graphs, SER, cooperative vectors).

**Slang** is the strongest default for new or multi-target shader code. Khronos has hosted it since November 2024, the Vulkan Guide documents it as a first-class language, and NVIDIA's descriptor-heap samples and nvpro-samples use it ([Khronos](https://www.khronos.org/news/permalink/khronos-group-launches-slang-initiative-hosting-open-source-compiler-contributed-by-nvidia); [Vulkan Guide: Slang](https://docs.vulkan.org/guide/latest/slang.html)). It accepts HLSL input, emits DXIL, SPIR-V and Metal, and adds modules, generics, interfaces and a reflection API that can drive layout creation. Two traps stand out. The command line and the library API have different default matrix layouts, so set the layout explicitly. Slang also defines no target macros automatically. Interface-based dispatch is "usually" specialized away, not always, so profile it. For debugging, glslang (`-gVS`), DXC (`-fspv-debug=vulkan-with-source`) and Slang all emit NonSemantic.Shader.DebugInfo.100, which RenderDoc uses for source-level debugging ([RenderDoc](https://renderdoc.org/docs/how/how_shader_debug_info.html)). Debug printf works through the validation layers.

Driver compilers lower SPIR-V into their own IR and re-optimize it: NIR into ACO on RADV, NIR into the Intel backend or NAK on Mesa, and proprietary backends elsewhere. As a result, **spirv-opt `-O` rarely changes the final ISA**. A 2026 tooling write-up warns it "is not a free win" and should be validated per driver ([techoverflow](https://techoverflow.net/2026/09/29/spir-v-tooling-for-vulkan-spirv-val-spirv-opt-spirv-dis-spirv-cross-and-runtime-reflection/)). Front-end work still pays where the backend cannot recover the information. That means legalizing DXC output, eliminating dead IO and bindings, specializing so drivers see constants, using explicit FP16 (RelaxedPrecision, which spirv-opt can add automatically for mobile), and avoiding unrolling that inflates driver compile time ([LunarG RelaxedPrecision](https://www.lunarg.com/wp-content/uploads/2019/09/Automatic-RelaxedPrecision-Decoration-and-Conversion-in-Spirv-Opt_r1.pdf)). The large shader-level wins are algorithmic and data-layout choices. AMD lists FP16 at double rate, `readFirstLane` scalarization, Gather4 for single-channel fetches, LDS padding against its 32 banks, 8×8 compute tiles with swizzle, and avoiding atan/acos at over 100 cycles. A full-screen pass in compute gains about 2% ([AMD RDNA guide](https://gpuopen.com/learn/rdna-performance-guide/)). Workgroup sizes that are multiples of 64 are the safe cross-vendor default. Query `subgroupSize` or set `requiredSubgroupSize` rather than hard-coding 32 or 64, and note that RADV exposes required subgroup size only for compute ([Mesa #7207](https://gitlab.freedesktop.org/mesa/mesa/-/issues/7207)).

**Stutter is a pipeline problem, and the 2026 toolkit is layered.** The base layer is a persisted VkPipelineCache wrapped in your own header carrying a data hash, vendor and device IDs, driver version and UUID. Validate that header before handing data to the driver, and write via temp-file-then-rename, because driver rollbacks corrupt caches ([zeux.io](https://zeux.io/2019/07/17/serializing-pipeline-cache/); [Roblox](https://corp.roblox.com/newsroom/2021/02/creating-a-robust-pipeline-cache-with-vulkan)). Compile on worker threads, because the driver spawns none ([AMD](https://gpuopen.com/learn/rdna-performance-guide/)). For combinations you did not predict, **graphics pipeline library** splits pipelines into vertex-input, pre-raster, fragment and output parts. Fast-link at first use, then build the link-time-optimized pipeline in the background and swap it in. Valve's Source 2 needed fewer than 40 interface libraries this way, and fast linking is supported on desktop NVIDIA, AMD and Intel ([Khronos GPL blog](https://www.khronos.org/blog/reducing-draw-time-hitching-with-vk-ext-graphics-pipeline-library)). **VK_KHR_pipeline_binary** (Roadmap 2026) gives the app explicit per-pipeline binaries and driver-computed keys that ignore irrelevant state, which makes it a natural dedupe key. It is on RADV, and on ANV and NVK from Mesa 26.0, but its status on Windows drivers is unconfirmed ([Khronos pipeline binary blog](https://www.khronos.org/blog/bringing-explicit-pipeline-caching-control-to-vulkan)). **Shader objects** suit engines built around dynamic state, especially on NVIDIA, but Khronos says "applications wanting something that behaves like pipelines should just use pipelines" ([shader object proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_shader_object.html)). The top layer is to enumerate the PSO set ahead of time, as Unreal's PSO precaching does at asset load. Unreal skips the draw while a PSO compiles rather than hitching, and warns that each compile thread can take about 2 GB ([UE PSO precaching](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine)). Specialization constants and "uber-shader first, specialize later" keep the module count manageable. Specialization constants reduce the number of SPIR-V variants but not the number of pipeline compiles.

## Native Linux is viable, but QA spans three driver families

The Linux driver landscape in 2026 has three families. **Mesa** (RADV, ANV, NVK) ships quarterly: 26.0 in February, 26.1 in May, 26.2 in August and 26.3 on 9 November 2026, with new extensions landing across drivers within a release or two ([Mesa 26.0.0 notes](https://docs.mesa3d.org/relnotes/26.0.0.html); [Mesa 26.2.0 notes](https://docs.mesa3d.org/relnotes/26.2.0.html)). RADV, driven by Valve, is the Steam Deck driver and the reference for SteamOS. Mesa 26.3 gave it a native VK_AMD_anti_lag implementation ([Phoronix](https://phoronix.com/news/Mesa-26.3-RADV-VK_AMD_anti_lag)). **NVIDIA's proprietary driver** is what most NVIDIA users run. Its 595 branch brought descriptor heap, present timing and better swapchain behavior ([GamingOnLinux](https://www.gamingonlinux.com/2026/03/nvidia-driver-595-58-03-released-as-the-big-new-recommended-stable-driver-for-linux)). NVK is a conformant Vulkan 1.4 driver from Turing to Blackwell and gained mesh shaders in 26.2, but it still trails clearly in compute and ray tracing ([Collabora](https://www.collabora.com/news-and-blog/news-and-events/mesa-25.2-brings-new-hardware-support-for-nouveau-users.html)). Nova, the Rust kernel driver, is "not yet ready in a state for end users" ([Phoronix, LPC 2026](https://www.phoronix.com/news/Nova-Driver-LPC-2026)). The third family, Turnip, PanVK and Honeykrisp, matters only for ARM Linux. RADV compiles with ACO, whose codegen and compile times differ from AMD's Windows compiler, so profile shader hitches on Linux AMD separately. Gate features on extension and feature queries, never on Mesa version strings, and log driverID, driverInfo and conformanceVersion with every device-lost report.

**Presentation has largely closed the gap with Windows.** Wayland FIFO has blocked correctly since Mesa 24.3 via fifo-v1. VK_EXT_present_timing ships in Mesa (Wayland from 26.1, X11/XWayland from 26.2) and in NVIDIA 595 ([Phoronix](https://www.phoronix.com/news/Mesa-VK_EXT_present_timing)). HDR works through the upstream color-management protocol, which Mesa WSI has implemented directly since 25.1 ([ArchWiki HDR](https://wiki.archlinux.org/title/HDR)). Explicit sync fixed NVIDIA's Wayland flicker starting with driver 555 ([GamingOnLinux](https://gamingonlinux.com/2024/06/nvidia-driver-555-58-released-as-stable-bringing-wayland-explicit-sync/page=2)). Pacing is the remaining app-side work, and Themaister's July 2026 measurements on an RX 9070 XT quantify it. Under fixed-refresh 60 Hz FIFO, GPU-idle-to-present latency averaged **32.3 ms**, and blocking on the previous frame with present_wait2 cut it to **15.5 ms**. With anti-lag, GPU-bound Cyberpunk with RT dropped input-to-present latency from **75.9 ms to 50.0 ms** ([Themaister, July 2026](https://themaister.net/blog/2026/07/)). The lesson is to limit outstanding presents with present_wait(2), adopt present_timing where exposed, and enable anti-lag on RADV. For windowing, SDL3 is the de facto choice. It prefers native Wayland only when the compositor supports fifo-v1, falls back to XWayland otherwise, and handles Steam Input and high-DPI ([libsdl discourse](https://discourse.libsdl.org/t/is-wayland-really-default/61737)).

For distribution, build inside the Steam Runtime SDK container and target **Steam Linux Runtime 4.0 (steamrt4)**, which Valve calls "the recommended environment for developers of new native Linux games" ([steam-runtime](https://github.com/ValveSoftware/steam-runtime)). The runtime imports host GPU drivers, so link against or dlopen the system `libvulkan.so.1` (volk makes this easy) and never bundle a loader or ICDs. Ship SPIR-V, not driver binaries. Note that Linux SDK 1.4.357 binaries need glibc 2.35+ ([LunarG](https://lunarg.com/lunarg-releases-vulkan-sdk-1-4-357-0/)). Valve's policy carries a strategic risk. Since 2022, Steam Deck testing has used the native build first and fallen back to Proton only if the native build fails, so **a mediocre native port can rate worse than the Windows build under Proton** ([GamingOnLinux](https://www.gamingonlinux.com/2022/02/valve-clarifies-how-they-test-native-linux-or-proton-for-steam-deck)). A native build must therefore be at least as good as vkd3d-proton running the D3D12 build. Running the D3D12 build under vkd3d-proton also gives a free correctness and performance reference during bring-up. Linux debugging tools are strong. `MESA_VK_TRACE=rgp` captures AMD RGP/RMV/RRA traces without the proprietary driver. `RADV_DEBUG=hang` writes hang reports, VK_KHR_device_fault is available on RADV from 26.2, and Nsight Aftermath supports Vulkan on Linux ([Mesa envvars](https://docs.mesa3d.org/envvars.html); [Aftermath guide](https://docs.nvidia.com/nsight-aftermath/UserGuide/index.html)).

## A seven-phase migration plan for ReGPU-V

The research supports a migration that converges the two APIs before writing Vulkan code, keeps D3D12 as the golden reference throughout, and adopts 2026 extensions only behind capability detection. The phases below synthesize the vkd3d-proton baseline, NRI's design, the vendor guides and the Larian and Godot lessons.

| Phase | Work | Exit criterion |
|---|---|---|
| 0. Modernize D3D12 | Move to Enhanced Barriers; move binding to SM6.6 `ResourceDescriptorHeap` bindless; restrict ExecuteIndirect to draw/dispatch where possible; add a render graph if absent | D3D12 path runs clean under debug layer/GBV with no legacy states |
| 1. Thin RHI | Extract a D3D12-shaped RHI (sync/access/layout barriers, global descriptor heap, push constants, indirect) using NRI as reference; startup-switchable backends | D3D12 backend unchanged in behavior and performance behind the RHI |
| 2. Shared shaders | One source: HLSL+DXC with register shifts, `-fvk-use-dx-layout`, `-fspv-target-env=vulkan1.3`, Y-flip via viewport; or migrate to Slang; emit NonSemantic debug info in dev builds | Every shader compiles to DXIL and SPIR-V in CI with spirv-val passing |
| 3. Vulkan baseline | Vulkan 1.3 + Roadmap 2022 + robustness2 + push/mutable descriptors; dynamic rendering, sync2, timeline semaphores, VMA, volk, vk-bootstrap; global bindless set + BDA | Image-diff parity with D3D12 on NVIDIA, RADV and ANV; zero validation and sync-validation errors |
| 4. Pipelines | Offline PSO enumeration, threaded precompile, robust cache header; GPL fast-link + background LTO for misses; pipeline_binary where present | No PSO compile on the render thread in captured play sessions |
| 5. Fast paths | descriptor_heap, unified_image_layouts, device_generated_commands, present_wait2/present_timing, anti-lag; mesh/RT as tiers | Each path toggleable and benchmarked against baseline per vendor |
| 6. Linux ship | SDL3, steamrt4 SDK container, Wayland+X11 testing, VRR and fixed refresh, Deck at 1280×800 in gamescope; compare against vkd3d-proton running the D3D12 build | Native build matches or beats Proton on Deck |

Validation should run continuously, not as a final phase. Debug builds should enable core validation, synchronization validation, periodic GPU-AV (Scoped GPU-AV keeps the overhead tolerable) and the Profiles layer set to the declared baseline ([LunarG 1.4.357.0](https://lunarg.com/lunarg-releases-vulkan-sdk-1-4-357-0/)). The AMD Best Practices layer checks catch vendor-specific hazards. Image-diff testing between backends catches Y-flip, depth and sRGB divergences early, when they are cheap to fix. The Larian experience argues for investing in Vulkan expertise before the backend ships, not after.

## Conclusion

The defining shift of 2026 is that Vulkan has moved toward D3D12 rather than the reverse. Descriptor heaps, unified image layouts, maintenance11's D3D compatibility fixes and device-generated commands were all shaped by Valve and vkd3d-proton's experience translating D3D12. A D3D12-first renderer that has adopted enhanced barriers and SM6.6 bindless is therefore closer to idiomatic modern Vulkan than a 2018-era "native" Vulkan engine built on render passes, descriptor sets per draw and secondary command buffers. The porting cost now sits less in API semantics than in the operational layers around the API: pipeline precompilation, multi-driver QA across Mesa and NVIDIA, Linux presentation pacing, and the toolchain choice between DXC and Slang.

The open risks are coverage and evidence, not capability. The newest fast paths reach only a third or less of reported devices. No vendor has published measured gains for descriptor heap over bindless sets, for GPL or shader objects over precompiled PSOs, or for async compute on current architectures. AMD's Windows support for descriptor heap, Windows support for pipeline_binary, and whether a "Vulkan 1.5" will roll up the maintenance extensions all remain unknown. ReGPU-V should treat its own per-vendor benchmarks as the deciding evidence, build every 2026 feature as a toggle against the 1.3 baseline, and revisit the floor once Roadmap 2026 hardware dominates the installed base.
